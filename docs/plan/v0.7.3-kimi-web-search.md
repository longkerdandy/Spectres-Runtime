## 2. Context

v0.3.1 integrated Agno's `TavilyTools` and retained `WebsiteTools.read_url` for full-page reads. Kimi Code exposes the same style of operation through Moonshot's search endpoint. Runtime will implement that client itself rather than import Kimi Code or reuse its OAuth files.

Confirmed Kimi Code behavior:

- Managed OAuth appends `/search` to `https://api.kimi.com/coding/v1`; the resulting endpoint is `https://api.kimi.com/coding/v1/search`.
- The request is authenticated with `Authorization: Bearer <token>` and sends `text_query`.
- Current Kimi Code source also sends `search_mode: "links"`; Runtime will adopt that field explicitly.
- The response contains `search_results`, whose entries may include `title`, `url`, `snippet`, `date`, and `site_name`.
- The client returns search summaries, not full pages. Runtime will keep `WebsiteTools.read_url` as the page-reading tool.

Compatibility decision: `WEB_SEARCH_BACKEND` explicitly selects `kimi` (the default) or `tavily`, and the selected backend is registered only when its credential is configured. Credentials for an unselected backend neither activate it nor provide automatic fallback. The two search Toolkits must never be registered together. This milestone does not remove the existing Tavily configuration or dependency.

Read first: `AGENTS.md`, `docs/plan/v0.3.1-web-search-tavily.md`, `docs/adr/0006-web-search-tool-tavily.md`, `src/spectres/tools/builtin.py`, and `src/spectres/config.py`.

## 3. Agno 3.1.2 Source Findings

The implementation must account for the following verified Agno behavior:

1. **No Kimi/Tavily-specific Agent dispatch exists.** `agno/agent/_tools.py` handles a `Toolkit` by iterating `get_functions()` or `get_async_functions()`, calling `Function.process_entrypoint()`, and passing the resulting functions to the model. Search Toolkits follow the ordinary function-tool path.
2. **The public method contract matters.** `agno/tools/function.py` derives the model-facing description and JSON schema from the callable signature, type annotations, and docstring. The tool will therefore expose one required `query: str` argument with an explicit Google-style docstring. It will not expose an unsupported `max_results` argument.
3. **Sync and async registration are distinct.** `Toolkit` stores them separately; async runs prefer `get_async_functions()`. Runtime will provide both entrypoints under the same public name, using `tools=[...]` and `async_tools=[(async_callable, "web_search_using_kimi")]`.
4. **Toolkit timeout is not an HTTP timeout enforcement mechanism.** Agno stores the `timeout` attribute but does not wrap arbitrary Toolkit HTTP calls with it. The Kimi implementation must pass its timeout directly to both `httpx.Client` and `httpx.AsyncClient` calls.
5. **Instructions are opt-in.** Toolkit instructions enter the Agent prompt only when `add_instructions=True`. This milestone leaves that disabled; usage guidance belongs in the tool docstring so no hidden global instruction is introduced.
6. **Duplicate function names are skipped.** Registration order can silently hide a duplicate search function. The registry tests must prove that exactly one search Toolkit and one public search function are present in every configuration.
7. **Result shaping belongs to the Toolkit.** Tavily filters fields and applies its own output budget. Agno does not turn Kimi's response into citations or fetch result pages automatically. The custom Toolkit must whitelist fields, bound output size, and return a JSON string.
8. **Provider-native search is separate.** OpenAI Responses deep-research models can inject `web_search_preview`; Gemini can add Google Search through its `search`/`grounding` options. This milestone adds neither option and must not represent the custom Toolkit as provider-native search.
9. **AG-UI needs no search-specific event.** The Kimi function uses the existing tool-call lifecycle. No custom AG-UI event or Runtime patch is required.

## 5. Design

### 5.1 Configuration

| Environment variable | Settings field | Behavior |
|----------------------|----------------|----------|
| `WEB_SEARCH_BACKEND` | `web_search_backend: Literal["kimi", "tavily"]` | Defaults to `kimi`; explicitly selects the only eligible search Toolkit. Future backends extend the allowed values and registration branches. |
| `KIMI_WEB_SEARCH_API_KEY` | `kimi_web_search_api_key: str \| None` | Optional; blank disables Kimi even when selected. Never logged or returned in an error. |
| `KIMI_WEB_SEARCH_BASE_URL` | `kimi_web_search_base_url: str` | Defaults to `https://api.kimi.com/coding/v1/search`; override supports another compatible endpoint, including the global deployment. |
| `TAVILY_API_KEY` | `tavily_api_key: str \| None` | Optional existing credential; used only when `tavily` is selected. Its example section is fully commented by default. |

Update both the development and test sections of `.env.example` in full. Do not edit `.env`, `.env.local`, `.env.test`, or `.env.test.local`.

### 5.2 Backend Selection

`get_builtin_tools()` keeps Calculator, Shell, and Website registration unchanged, then applies:

```text
WEB_SEARCH_BACKEND=kimi   + KIMI_WEB_SEARCH_API_KEY set → register KimiWebSearchTools only
WEB_SEARCH_BACKEND=tavily + TAVILY_API_KEY set          → register TavilyTools(search_depth="basic") only
selected credential missing                              → register no web-search Toolkit
unselected credential present                            → no effect; never fall back
```

The Kimi public function name is `web_search_using_kimi`; its Toolkit name is `kimi_web_search`. Existing Tavily names remain unchanged for alternative-backend compatibility.

### 5.3 HTTP Contract

Both sync and async implementations send:

```http
POST <KIMI_WEB_SEARCH_BASE_URL>
Authorization: Bearer <KIMI_WEB_SEARCH_API_KEY>
Content-Type: application/json

{"text_query": "<query>", "search_mode": "links"}
```

Implementation requirements:

- Trim `query`; reject a blank query without making a network request.
- Use a 15-second HTTP timeout in the Toolkit constructor and pass it explicitly to `httpx`.
- Use per-call client context managers so the Toolkit needs no Agno connection lifecycle or process-global client.
- Share request construction, response validation, formatting, and error mapping between sync and async paths.
- Accept only HTTP 200 as success; do not retry automatically.
- Do not send Kimi Code's `X-Msh-Tool-Call-Id` in this milestone because the Agno entrypoint does not need that correlation field.

### 5.4 Result Contract

Return UTF-8 JSON text with `ensure_ascii=False`:

```json
{
  "query": "normalized query",
  "results": [
    {
      "title": "title or empty string",
      "url": "URL or empty string",
      "snippet": "summary or empty string",
      "date": "optional date",
      "site_name": "optional site name"
    }
  ],
  "truncated": false
}
```

- Validate the response as JSON and read only `search_results`.
- Ignore unneeded upstream fields such as `content`, `icon`, and `mime`; do not pass raw response objects to the model.
- Return at most 10 results and at most 20,000 serialized characters. When limiting output, preserve valid JSON and set `truncated: true`; shorten oversized snippets rather than dropping the only result.
- A valid empty response returns `results: []`, not an exception.
- The docstring tells the model that results are summaries and that it should use `read_url` when full page content is required and cite source URLs in its answer.

### 5.5 Failure Contract

External failures return a controlled JSON error object instead of leaking an exception or raw response body:

```json
{
  "query": "normalized query",
  "results": [],
  "error": {
    "type": "authentication | rate_limit | http | timeout | network | invalid_response",
    "message": "safe diagnostic message",
    "status": 401
  }
}
```

`status` is included only for HTTP responses. Map 401/403 to `authentication`, 429 to `rate_limit`, timeouts and network failures separately, and malformed success payloads to `invalid_response`. Log handled failures without the bearer token or response body. Do not expose credentials through exception strings.

## 8. Verification Notes

- Unit tests must use mocked HTTP transport; no unit test may depend on a real Kimi key or external network.
- Inspect the actual Agno `Function` objects rather than testing only a direct Python method call. This catches signature, docstring, sync/async registration, and duplicate-name problems.
- During live verification, confirm the Runtime process uses the intended `KIMI_WEB_SEARCH_BASE_URL` without printing the credential.
- Run `tests/test_agui.py` explicitly because v0.7.2 changes the adjacent tool-event lifecycle, even though this milestone adds no AG-UI patch.
- If the real API rejects `search_mode: "links"`, stop and reconcile the request with the deployed Kimi API rather than silently falling back to another provider or dropping the field without recording the change.
