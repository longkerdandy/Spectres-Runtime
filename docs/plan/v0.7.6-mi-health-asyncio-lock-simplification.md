# Milestone Plan — v0.7.6

> Simplify Mi Health synchronization concurrency to one Runtime instance with per-owner `asyncio.Lock` instances and volatile active/latest run snapshots, while preserving asynchronous execution, safe status responses, and durable health checkpoints.

## 2. Context

Runtime v0.7.5 introduces a Mi Health-owned run table, JSONB stream snapshots, a
partial unique active-run index, atomic database run claiming, startup interruption
reconciliation, and unbind cleanup for persisted run history. These capabilities
support durable run observation and future multi-process execution.

The current product deployment has one Runtime instance, and durable run history,
cross-process execution ownership, and automatic restart recovery are not required
in the foreseeable future. The durable run layer is therefore more infrastructure
than the product needs.

The simpler design must preserve the useful behavior:

- one manual synchronization per owner at a time;
- `202 Accepted` with background execution rather than a long browser wait;
- queued/running progress and the latest terminal result while the process lives;
- reload/navigation recovery while the same Runtime process is running;
- independent current checkpoint health and authoritative Data coverage;
- active-sync unbind conflicts, safe errors, owner isolation, and privacy;
- idempotent health upserts and the existing backfill/overlap behavior.

## 3. Confirmed Product Decisions

1. **Single instance is an explicit constraint.** Use `asyncio.Lock` only inside
   the single Runtime event loop. Do not imply safety across workers, processes,
   or machines.
2. **One lock per owner.** Different users can synchronize independently. A lock
   is held for the complete background execution, not only during run creation.
3. **No queue.** A second start for the same owner returns
   `409 sync_in_progress` immediately. No request waits for the lock and no
   automatic retry occurs.
4. **Run presentation is volatile.** Active and latest run snapshots live in
   memory. Browser reload and navigation recover them while the Runtime process
   remains alive; Runtime restart clears them.
5. **Checkpoints remain durable.** `health_ingestion_states`, committed health
   records, Data coverage, backfill state, and current stream health remain
   authoritative and survive restart.
6. **No restart reconstruction.** After restart, `active_run` and `last_run` are
   null. Do not synthesize an `interrupted` run or derive a historical run from
   checkpoints. The user can explicitly start a new synchronization.
7. **Keep the public response shape.** Reuse `SyncRunResponse`,
   `SyncStatusResponse`, stream outcomes, error codes, and HTTP statuses so the
   Web Client does not need another API or state layer. Unsupported future trigger
   and status enum values may remain in the schema for compatibility, but this
   milestone produces manual runs only.
8. **Do not destructively migrate legacy history.** Retain the v0.7.5 migration
   and legacy `mi_health_sync_runs` table for upgrade compatibility, but stop all
   status reads and execution writes against it. Unbind must still delete the
   current owner's legacy rows for privacy. No new migration or automatic table
   drop is included.
9. **No new infrastructure or dependency.** Do not add Redis, advisory locks, a
   distributed-lock library, a queue, a scheduler, or a state-management library.
10. **Async endpoints own memory access.** Manual start, status, unbind, and
    background run-state transitions must execute on the Runtime event loop.
    Do not read or mutate the in-memory registry from a threadpool route.

## 4. Scope

### 4.1 In Scope

1. Replace the database run service with a focused in-memory synchronization
   coordinator using per-owner `asyncio.Lock` instances.
2. Preserve `202` manual start, background execution, active progress, latest
   terminal result, and safe per-stream outcomes in memory.
3. Make the manual-start, sync-status, and unbind routes asynchronous so all
   registry access stays on the event loop.
4. Use the same owner lock to reject unbind during active execution and to prevent
   start/unbind races.
5. Remove startup interruption reconciliation and active database-run claiming.
6. Preserve existing checkpoint, ingestion, backfill, incremental-overlap,
   session-renewal, mapping, and privacy behavior.
7. Retain legacy migration/table compatibility and owner-scoped legacy-history
   deletion during confirmed unbind.
8. Update Web Client restart-aware empty-state copy, both projects' living
   documentation, tests, and release metadata at release.
9. Verify same-process reload recovery and explicit restart behavior against real
   Runtime and Logto.

### 4.2 Out of Scope

- Multiple Uvicorn workers, multiple Runtime instances, distributed locks, Redis,
  Redlock, PostgreSQL advisory locks, and distributed queues.
- Durable active/latest runs, full run history, retention controls, and automatic
  restart recovery or interruption reconstruction.
- Scheduled Mi Health synchronization, Workflows, personal Schedules, cancellation,
  and per-stream manual retry.
- Changes to health models, provider mappings, backfill duration, overlap duration,
  pagination, or canonical ingestion contracts.
- A destructive migration that drops the legacy run table or deletes its history.
- New health-data presentation, administrator run views, or cross-user controls.

## 5. Target Design

### 5.1 Composition and state

Construct one `MiHealthSyncService` in the Extension composition root and inject
that same instance into the API router. Remove construction of
`MiHealthSyncRunService` and the `runs.interrupt_active()` startup call.

The service owns event-loop-local state equivalent to:

```text
_locks: dict[user_id, asyncio.Lock]
_active_runs: dict[user_id, SyncRun]
_last_runs: dict[user_id, SyncRun]
```

Create locks lazily for the small set of active Runtime users. Do not add a lock
cleanup protocol in this milestone. Continue generating server-side run ids and
safe stream snapshots so existing response schemas remain valid. Never accept an
owner id or run id from a request payload.

Keep run snapshots and transitions synchronous within the event loop. Update a
snapshot atomically between awaits and return an immutable/copy-validated response
so serialization cannot observe a partially applied transition.

### 5.2 Manual start

Make `POST /api/v1/extensions/mi-health/sync` an `async def` route and follow this
sequence:

1. Derive the owner through `require_user_id`.
2. Obtain the owner's lock without waiting. If it is already held, raise
   `SyncInProgressError`; the existing adapter maps it to `409`.
3. While holding the lock, validate the binding and create the queued in-memory
   snapshot. Release immediately if validation or creation fails.
4. Register the existing async execution function as a FastAPI background task,
   passing the verified owner and server-created run id.
5. Return the existing `202 SyncRunResponse`.

Lock acquisition and the decision to reject a duplicate must be one event-loop
critical section. Do not use `wait_for`, blocking acquisition, or automatic retry.

### 5.3 Background execution

The background executor uses the same service instance and follows this sequence:

1. Confirm that the verified owner's current active run has the server-created id;
   otherwise perform no work.
2. Mark it running and advance the existing per-stream snapshots in memory.
3. Preserve the existing bounded synchronization, one renewal/retry per stream,
   independent stream failures, safe failure stages, and aggregate outcomes.
4. Move the terminal snapshot from active to latest before releasing the lock.
5. Release the owner's lock in `finally` on success, expected failure, and
   unexpected exception.

Do not write run transitions to PostgreSQL. Health records and checkpoints continue
to commit through `HealthIngestionService` exactly as before.

### 5.4 Status reads

Make `GET /sync/status` an `async def` route. Read active/latest memory state only
on the event loop, then compose the response with the existing Core checkpoint
query. Do not acquire the execution lock for a status read.

The response contract remains:

```text
active_run: SyncRunResponse | null  # current-process active snapshot
last_run: SyncRunResponse | null    # latest current-process terminal snapshot
streams: SyncStreamHealthResponse[] # durable Core checkpoints
```

After a Runtime restart, the first two values are null. The streams still expose
`last_successful_window_end`, current health, and backfill completion from durable
checkpoints.

### 5.5 Unbind coordination

Move the unbind orchestration behind the same synchronization service instead of
injecting a run repository into `MiHealthBindingService`.

Make `DELETE /binding` asynchronous:

1. Derive the verified owner.
2. Try to acquire the owner's lock without waiting; an active run produces the
   existing `409 sync_in_progress`.
3. Hold the lock while `MiHealthBindingService` deletes the binding, QR attempts,
   current owner's Mi Fitness health contribution, checkpoints, and legacy Mi
   Health run rows.
4. Clear that owner's active/latest in-memory snapshots after successful deletion.
5. Release in `finally`; preserve all other owners and providers.

A failed unbind does not clear run presentation or fabricate success.

### 5.6 Disablement and restart

Extension disablement continues to block new REST work without claiming to cancel
an in-flight background synchronization. The lock and in-memory status remain until
that execution finishes; checkpoints and legacy rows remain untouched.

A Runtime process stop ends background work without a recovery attempt. Already
committed windows remain durable. After restart, a new service instance has empty
locks and active/latest maps. A later explicit sync follows the existing checkpoint
and backfill logic with idempotent upserts; it is not described as resuming the old
run.

## 6. Legacy Schema and Privacy

Retain `0002_mi_health_sync_runs` in Alembic history and retain the legacy table in
existing installations. Do not create a downgrade/destructive migration and do not
delete the table during registration.

Remove the active run repository, unique-active execution dependency, JSONB status
composition, and startup interruption logic. A minimal owner-scoped cleanup path
may retain the legacy model only to delete legacy rows during confirmed unbind.
No API status or execution path may read the legacy table.

All existing ownership, activation, safe-error, and privacy requirements remain.
Volatile snapshots contain only the current safe response fields: no owner id in
public responses, health values, Profile values, account identifiers, credentials,
provider payloads, or pagination cursors.

## 7. Web Client Coordination

No new Client milestone or API layer is required. During the coordinated
implementation, make only the necessary adjustments in the existing Web Client
v0.5.4 work:

- Replace the run-empty copy that says "No synchronization yet" with neutral copy
  such as "No synchronization run observed in this Runtime process." It must not
  contradict non-empty durable stream health after a restart.
- Explain that active/latest run presentation is current-process state, while Data
  coverage and current stream health are durable checkpoint state.
- Keep the existing API wrappers, 202 handling, active-only polling, reload
  recovery, six-column table, and all safe error handling.
- Do not infer an interrupted run or a successful terminal result when active
  status disappears across a Runtime restart.

Update both projects' architecture documents and agent guidance to remove claims
that run status is durable. The v0.7.5 plan remains a historical milestone; this
plan supersedes its durability direction without rewriting its record.
