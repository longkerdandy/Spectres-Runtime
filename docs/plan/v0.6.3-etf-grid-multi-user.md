# v0.6.3 — ETF Grid Multi-User Isolation

| Field | Value |
|-------|-------|
| **Status** | done |
| **Created** | 2026-11-01 |
| **Started** | 2026-11-01 |
| **Completed** | 2026-11-06 |
| **Goal** | Share ETF market history and valuation data across all users, isolate each user's trades, positions, and signals, and let administrators enable or disable the ETF symbols tracked by the extension without moving grid sizing parameters into the database. |

---

## 1. Background

ETF Grid currently predates the Runtime's per-user data boundary. Every
authenticated caller reads and mutates the same trade ledger and signal
snapshots through both REST and Agent tools. This was an explicit v0.6.x
exception; v0.6.3 removes that exception for ETF Grid user-owned data.

The intended ownership model is:

- **Shared market inputs**: candles and valuation series are fetched and
  stored once per symbol/index, not once per user.
- **Shared strategy configuration**: `ETF_GRID_PORTFOLIO` remains the source
  of `name`, `per_grid_amount`, `max_grids`, and `gate`. Those values are the
  same for every user and stay in configuration for this milestone.
- **Administrator-controlled symbol selection**: administrators choose which
  of the configured portfolio symbols are enabled for synchronization,
  status, and new signal computation.
- **Private user state**: trades are owned by exactly one user; positions and
  cost basis continue to be derived from that user's ledger; signals are
  private because their order advice depends on positions and open lots.
- **One system schedule**: the existing unowned schedule synchronizes shared
  data once and then recomputes signals for known ETF Grid users. It does not
  create one AgentOS schedule per user.

The administrator manages only the enabled/disabled selection in v0.6.3.
Adding a completely new ETF still means adding its strategy definition to
`ETF_GRID_PORTFOLIO`; the admin API cannot invent missing grid parameters.
This deliberately avoids a second strategy-configuration model and keeps the
milestone focused on isolation.

## 2. Current State

- `etf_grid_candles` and `etf_grid_valuation` already contain shared data and
  need no `user_id`.
- `etf_grid_trades` has no owner column. All ledger reads, writes, counts,
  and position replays are currently global.
- `etf_grid_signals` is keyed by `(symbol, trade_date)`, so identically dated
  computations for different users would overwrite each other.
- `compute_daily_signals()` replays the ledger and uses shares/open lots to
  produce order advice. Signals therefore cannot remain globally shared even
  though their candle and valuation inputs are shared.
- `ETF_GRID_PORTFOLIO` is loaded once at extension registration. It contains
  the complete strategy definitions and remains unchanged in meaning.
- `etf_grid_daily_sync` is an unowned system schedule targeting `/refresh`;
  the route currently performs one shared sync plus one shared computation.
- JWT authentication, Logto-owned roles, `agent_os:admin`, and Agno
  `user_isolation=True` are live. Extension tables and custom routes still
  need explicit ownership and authorization checks; framework isolation does
  not apply to them automatically.
- Agno tools can receive an injected `RunContext` whose `user_id` is the
  authenticated run owner. This is the required identity channel for private
  ETF Grid tool calls.
- There is still no production dataset or Alembic tooling. Development data
  may be reset, as in the earlier isolation milestones.

## 3. Design

### 3.1 Effective portfolio and administrator selection

Add an extension-owned `etf_grid_instruments` table:

| Column | Type | Notes |
|--------|------|-------|
| `symbol` | String(16) PK | Canonical FTShare full code; must exist in `ETF_GRID_PORTFOLIO` |
| `enabled` | Boolean NOT NULL | Whether the configured symbol participates in normal sync/status/compute |
| `updated_by` | String(128) NULL | Last administrator JWT subject; NULL for bootstrap rows |
| `created_at` | DateTime(tz) NOT NULL | Row creation time |
| `updated_at` | DateTime(tz) NOT NULL | Last selection change |

At extension registration, insert missing rows for all configured portfolio
symbols with `enabled=true`. Bootstrap is additive: restart must never
overwrite an administrator's existing enabled/disabled choice.

The effective portfolio is the join between enabled instrument rows and
`ETF_GRID_PORTFOLIO` strategy definitions. Configuration remains authoritative
for strategy values; the database is authoritative only for selection.
Configured symbols keep their existing per-symbol `per_grid_amount` and
`max_grids`, and every user sees those same values.

A disabled symbol:

- is excluded from normal `/status`, market-data sync, and new scheduled
  signal computation;
- remains in the database, including its candles, trades, and old signals;
- remains queryable in the owner's historical trade list;
- cannot be used for a new trade until re-enabled;
- is not physically deleted through the admin API.

Removing a symbol from `ETF_GRID_PORTFOLIO` also removes it from the effective
portfolio even if a stale instrument row remains. No dynamic strategy
fallback is invented for database rows missing from configuration.

### 3.2 Private trades and derived positions

Add `user_id String(128) NOT NULL` to `etf_grid_trades` and replace the
current access-pattern index with an index on
`(user_id, symbol, trade_date, id)`. The global autoincrement `id` remains the
primary key and replay ordering within one user/symbol remains
`(trade_date, id)`.

All `EtfGridLedgerService` operations take a required keyword-only `user_id`:

- `record_trade(user_id=..., ...)` stamps ownership server-side;
- `list_trades(user_id=..., ...)` and `count_trades(user_id=..., ...)` always
  filter by owner, including paginated totals and symbol/date filters;
- `get_positions(user_id=...)` and `get_position(user_id=..., symbol)` replay
  only that owner's rows.

There is no optional `user_id=None` path meaning "all users" in the normal
service API. Cross-user administrative browsing is not needed for this
milestone. Positions, average cost, realized P&L, and open lots remain derived
facts; no per-user position table is introduced.

### 3.3 Private signals over shared inputs

Add `user_id String(128)` to `etf_grid_signals` and change its primary key to
`(user_id, symbol, trade_date)`. Update the upsert conflict target and all
latest-signal queries accordingly. `latest_signals()` filters by owner and
uses `DISTINCT ON (user_id, symbol)` or the equivalent single-user form.

`compute_daily_signals(user_id=...)` and `get_portfolio_status(user_id=...)`
require an owner. For each enabled configured symbol they:

1. read the same shared candles and valuation rows as every other user;
2. replay only that user's ledger;
3. apply the same configured grid parameters;
4. persist or return only that user's signals and portfolio state.

Keep the complete per-user signal snapshot in v0.6.3. Do not split common
MA60/level fields into a separate shared snapshot table yet: the source market
history is already reused, and this extra normalization is unnecessary until
measurement shows a computation or storage problem.

### 3.4 REST identity and authorization

Normal private endpoints always operate on the authenticated caller:

```text
GET  /api/v1/extensions/etf-grid/status
GET  /api/v1/extensions/etf-grid/trades
POST /api/v1/extensions/etf-grid/trades
POST /api/v1/extensions/etf-grid/signals/compute
```

Use a small extension helper that requires `request.state.user_id` and returns
it as the owner. Never accept ownership from a request body, query parameter,
or forwarded property. Missing identity fails closed. This self-scope also
applies when an administrator uses a normal portfolio endpoint: it addresses
that administrator's own ledger rather than becoming an implicit unscoped
query. Do not directly propagate `get_scoped_user_id()`'s `None` admin result
into these services.

Instrument endpoints are:

```text
GET   /api/v1/extensions/etf-grid/instruments
GET   /api/v1/extensions/etf-grid/admin/instruments
PATCH /api/v1/extensions/etf-grid/admin/instruments/{symbol}
```

The regular list returns enabled effective symbols and their configured
strategy definitions. The admin list returns all configured symbols and their
selection state. The PATCH body contains only `enabled`; unknown symbols or
symbols absent from `ETF_GRID_PORTFOLIO` return 404/422 as appropriate.
Admin reads/writes require an explicit `agent_os:admin` check in the extension
router; ordinary authenticated users receive 403. Log an audit event with the
admin subject, symbol, previous state, and new state.

`POST /sync` and the schedule-facing `POST /refresh` become administrator or
trusted internal-scheduler operations rather than general user routes. Their
responses contain shared sync results and operational counts/errors, not
another user's trades or portfolio details.

### 3.5 Agent tools

Inject `RunContext` into every private ETF Grid tool and resolve the owner from
`run_context.user_id`. The LLM must never see or supply a `user_id` argument.
Missing identity returns the existing structured tool-error envelope.

Keep stable tool names and response envelopes:

- `get_grid_status` reads the current run owner's portfolio.
- `record_grid_trade` stamps the current run owner, regardless of note/source.
- `list_grid_trades` lists only the current run owner's trades.
- `refresh_grid_data` performs the shared market-data sync and then computes
  only the current run owner's signals. It never iterates other users.

No admin agent tools are added; symbol selection is managed through the admin
REST surface. Existing tool names keep the Web Client card registrations
stable.

### 3.6 Scheduler and refresh behavior

Retain one unowned `etf_grid_daily_sync` schedule and the `/refresh` carrier,
but change its work to two explicit phases:

1. Synchronize enabled symbols and the existing valuation series once.
2. Read distinct owner ids from the private trade ledger and run the normal
   per-user signal computation for each known ETF Grid user.

Each user's computation uses the required `user_id` service argument and has
an independent error boundary. One user's failure must not repeat market-data
fetching or prevent other users from being computed. Do not create one Agno
schedule per user and do not have the extension query Agno's user directory.

A user with no trades is not yet in the scheduled known-user set; their first
manual `/signals/compute` or `refresh_grid_data` still produces zero-position
advice. Once they record a trade, subsequent scheduled refreshes include them.
This is the deliberate lightweight alternative to adding user profile or
subscription tables in this milestone.

Preserve the scheduler HTTP semantics: all market-data sources failing returns
502; an unexpected shared-pipeline failure returns 5xx; partial source or
per-user computation failures may return 200 with structured `errors` so long
as usable shared data was produced. Audit logs may include user ids and counts,
but not private ledger contents.

### 3.7 Schema rollout

`metadata.create_all()` cannot add ownership columns or change primary keys.
This milestone continues the clean-slate development rollout: document the
required development database reset/rebuild and do not introduce Alembic just
for this change.

If the owner elects to preserve a development ledger, use a reviewed one-off
SQL/backfill procedure that assigns every existing trade to one explicitly
named owner, rebuilds the signal table, and creates/bootstrap the instrument
rows. Never duplicate the old shared ledger to every user and never guess an
owner from current login order. Existing signals are derived data and may be
recomputed after ownership is established.

## 4. Scope

### 4.1 In Scope

1. Add database-backed enabled/disabled selection for symbols already defined
   in `ETF_GRID_PORTFOLIO`, with idempotent startup bootstrap.
2. Add `user_id` ownership to trades and signals; enforce it in every ledger,
   position, signal, status, and computation service method.
3. Keep candles and valuation global and ensure scheduled synchronization is
   independent of user count.
4. Resolve REST and Agent-tool ownership from server-authenticated identity.
5. Add explicit admin authorization for instrument selection and global
   sync/refresh routes.
6. Update `/refresh` to sync once and recompute all known users without
   per-user schedules or repeated provider calls.
7. Add unit and real-PostgreSQL integration coverage for two-user isolation,
   admin selection, tool identity, scheduler fan-out, and shared-data reuse.
8. Update architecture documentation to remove the ETF Grid shared-data
   exception and describe the new public/private table contract.

### 4.2 Out of Scope

- Per-user `per_grid_amount`, `max_grids`, grid-step, gate, or subscription
  overrides.
- Admin editing of names, grid sizing, gates, or arbitrary symbols absent from
  `ETF_GRID_PORTFOLIO`.
- General multi-index valuation support; the existing configured 930914 gate
  remains the only valuation source in this milestone.
- A separate shared derived-market-snapshot table or computation cache.
- Per-user AgentOS schedules, background workers, or notification pipelines.
- Cross-user admin portfolio/trade browsing APIs and admin Agent tools.
- PostgreSQL RLS, per-user schemas, or per-user databases.
- Alembic adoption or a general production migration framework.
- Web Client implementation; existing normal ETF Grid pages continue calling
  the same self-scoped routes, and any admin console presentation is separate.

## 5. Success Criteria

- [x] Two users can trade the same enabled ETF and receive independent trade
  histories, positions, average costs, realized/unrealized P&L, and signals.
- [x] A same-day signal recompute for user A never changes user B's row; their
  different holdings can produce different order advice from identical market
  inputs.
- [x] Every private REST read/write and Agent tool derives ownership from the
  authenticated identity; spoofed body/query/tool `user_id` values cannot
  cross the boundary, and missing identity fails closed.
- [x] `etf_grid_candles` and `etf_grid_valuation` have no user dimension, and a
  scheduled refresh performs one provider sync per enabled symbol/index rather
  than one per user.
- [x] Admin can enable/disable any symbol present in `ETF_GRID_PORTFOLIO`;
  ordinary users receive 403 on admin operations, restarts preserve admin
  choices, and disabled symbols retain historical data.
- [x] `per_grid_amount` and `max_grids` still come only from
  `ETF_GRID_PORTFOLIO` and are identical across users for a given symbol.
- [x] The single unowned schedule syncs shared data once and computes all
  known users independently; a user without trades can still compute manually.
- [x] Existing auth, authorization, framework isolation, API validation, and
  scheduler regression suites remain green.
- [x] Runtime quality checks (`ruff`, formatting, `mypy`, `pytest`) pass
  locally and on CI, including real-DB integration tests.
