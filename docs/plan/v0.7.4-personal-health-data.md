## 2. Context

Runtime already stores an encrypted Xiaomi binding and can renew its health
session. It does not yet persist health metrics. Live owner-approved validation
on 2026-11-16 confirmed usable daily activity, heart-rate, sleep, SpO2, weight,
and body-composition records, plus raw sleep sessions. Sport, stress, and
abnormal-heart-beat reads succeeded but had no records on the validation
account.

Mi Health is only the first data channel. Personal health data belongs to
Spectres Core, not to that channel. The canonical schema must therefore describe
general health concepts rather than mirror Xiaomi field names or live under
`mi_health_*` tables. A future provider must be able to reuse the same tables,
ingestion service, and query contracts without a Core schema rewrite.

Database initialization and evolution need the same ownership boundary. Core
provides migration infrastructure and migrates Core-owned tables. Each Extension
owns its schema and migration history and invokes the shared migration
infrastructure during registration. The project currently has no migration
dependency: Runtime state and Extensions call `metadata.create_all()`
independently. This milestone replaces those calls with reviewed Alembic
migrations without teaching Core any Extension table structure. Agno-managed
tables and Logto's separate database remain outside this boundary.

The first product purpose is future lifestyle guidance from trends, not medical
diagnosis or a precise nutrition prescription. Dense raw time series and an
advice engine remain out of scope.

## 3. Confirmed Architecture Decisions

1. **Core owns personal health data.** Canonical health models, ingestion
   contracts, repositories, and future query services live under
   `src/spectres/health/` and use `health_*` tables.
2. **Providers are adapters.** Mi Health authenticates and reads Xiaomi, maps
   provider records into Core contracts, and supplies a stable provider id such
   as `mi_fitness`. Core never imports Extension code or Xiaomi-specific fields.
3. **One schema, explicit provenance.** Every health row carries `provider` and
   provider record metadata. Provider identity is data, not part of table names.
4. **Core owns migration infrastructure and Core schema.** Alembic support,
   shared locking/execution utilities, Runtime extension state, and `health_*`
   migrations are Core responsibilities.
5. **Extensions own their schemas.** Each Extension keeps its models and
   migrations together and invokes the Core migration utility during
   registration. Core never defines or owns Extension DDL or migration history.
6. **Agno and Logto retain their own schemas.** Do not migrate or modify
   `ai.agno_*` tables or Logto's separate database through Runtime migrations.
7. **Current state and history are different.** Profile context and ingestion
   checkpoints keep current rows. Health measurements remain longitudinal.
8. **History is upserted, not append-only.** Providers can correct existing
   records. Re-reading a record updates the same row rather than creating a
   duplicate or immutable revision log.
9. **No duplicate latest-metric tables.** Latest weight, sleep, and daily
   activity are queries over history tables.
10. **Missing is not zero.** Activity zeros can be real. Heart rate, SpO2,
    sleep-stage breakdowns, and body-composition zeros often mean unavailable
    and become `NULL` according to explicit mapping rules.
11. **Provider unlink is provider-scoped.** Explicit Mi Health unbinding deletes
    that provider's contributed health rows, but must never delete another
    provider's data. Reauthentication without unbinding preserves history.

## 4. Scope

### 4.1 In Scope

1. Add Alembic, a schema-agnostic Core migration utility, independent migration
   namespaces, locks, and migration tests.
2. Add Core migrations for Runtime extension state and the new health schema.
   Replace Runtime extension-state `create_all()` with the Core migration step.
3. Add Extension-local baseline migrations for ETF Grid and Mi Health. Invoke
   them during each Extension's registration through the shared utility and
   remove Extension `create_all()` calls without moving their DDL into Core.
4. Add the Core `spectres.health` package, typed provider-neutral ingestion
   contracts, SQLAlchemy models, repositories, and six `health_*` tables.
5. Add validated Mi Fitness mapping for Profile, selected daily summaries, raw
   sleep, weight/body composition, and workout summaries.
6. Add owner-triggered initial backfill and incremental synchronization using
   bounded time windows, complete in-memory pagination, overlap, and idempotent
   upserts.
7. Preserve provider provenance and selected raw payloads; never persist an
   opaque provider page cursor as a durable checkpoint.
8. Implement provider-scoped health cleanup during explicit Mi Health unbinding,
   while preserving other providers and all data during Extension disablement.
9. Add owner-isolation, migration, real-PostgreSQL, synthetic-fixture,
   correction/deletion, and live sync/replay verification.
10. Update `AGENTS.md`, living architecture, and project guidance during
    implementation to reflect Core health ownership and the Core/Extension
    migration boundary.
11. Set the package version to `0.7.4` only when the milestone is released.

### 4.2 Out of Scope

- Health recommendations, diet plans, medical interpretation, or proactive
  notifications.
- Food, allergy, medication, disease, or manual lifestyle-journal tables.
- Agent Tools, Workflows, system or personal Schedules, and unattended
  cross-user synchronization.
- A second health provider and automatic cross-provider conflict resolution or
  duplicate measurement merging.
- Dense raw heart-rate, step, calorie, SpO2, stress, HRV, or GPS time series.
- Workout-detail/FDS downloads, workout tracks, and scale multi-user attribution.
- Friendly device naming or a device registry.
- Stress and abnormal-heart-event persistence until real records and semantics
  are validated.
- Migration of Agno-owned or Logto-owned schemas.
- Core-owned baselines, DDL, or migration history for Extension-owned tables.
- Public cross-user reporting or administrator access to another user's health
  data.

## 5. Module and Dependency Boundaries

```text
src/spectres/
├── db/
│   ├── migration.py       # Schema-agnostic Alembic execution and locking
│   ├── migrations/        # Core-owned schema only
│   │   ├── env.py
│   │   └── versions/
│   └── postgres.py
├── health/
│   ├── models.py          # Current Core ORM shape; no provider imports
│   ├── contracts.py       # Typed canonical ingestion inputs
│   ├── ingestion.py       # Provider-neutral upsert and cleanup services
│   └── queries.py         # Owner-scoped current/history query boundary
└── extensions/
    ├── etf_grid/
    │   ├── models.py
    │   └── migrations/    # ETF Grid-owned schema history
    └── mi_health/
        ├── xiaomi.py      # Provider HTTP and protocol behavior
        ├── mapping.py     # Xiaomi -> Core health contracts
        ├── models.py
        ├── migrations/    # Mi Health-owned schema history
        └── service/       # Binding, session, and provider sync orchestration
```

Dependency direction is strictly:

```text
Mi Health Extension  -> Core health contracts/services -> health_* tables
Mi Health register   -> Core generic migration utility
Core health          -X-> any Extension
Core migration files -X-> Extension models, tables, or runtime code
```

Core migration files contain only Core-owned schema operations. Extension
migration files live beside the Extension's models and contain only that
Extension's schema operations. The shared migration utility executes a supplied
script location but has no knowledge of the tables those scripts define.

The Mi Health composition root constructs the Core ingestion service with the
shared engine/session factory and injects it into its sync adapter. Core services
use explicit session injection and no process-global database helper. Future
Agent query tools consume Core health query services, not Mi Health tables.

## 6. Database Initialization and Migration Ownership

### 6.1 Shared migration infrastructure

Add Alembic as a direct Runtime dependency; it is not currently present in
`pyproject.toml` or `uv.lock`. The Core utility accepts an engine, migration
script location, version-table name, and lock namespace. It uses the existing
`PostgresDb.db_engine` and connection pool without interpreting the supplied
schema operations.

Use independent migration namespaces:

| Namespace | Version table | Schema owner |
|-----------|---------------|--------------|
| Runtime Core | `runtime_schema_version` | Core Runtime state and `health_*` |
| ETF Grid | `etf_grid_schema_version` | ETF Grid Extension |
| Mi Health | `mi_health_schema_version` | Mi Health Extension |

Serialize migrations within each namespace with a distinct PostgreSQL advisory
lock. Independent namespaces must not overwrite one another's Alembic version or
share a global migration head. Do not run autogenerate, downgrade, or destructive
repair during application startup or Extension registration.

### 6.2 Startup and registration sequence

```text
get_postgres_db()
    -> migrate Core schema (Runtime extension state and health_*)
    -> load each discovered Extension
         -> run that Extension's local migrations through the Core utility
         -> construct and register its services
    -> initialize Extension activation state
    -> assemble AgentOS
```

A Core migration failure prevents Extension loading. An Extension migration
failure aborts that Extension's registration through the existing loader error
path and cannot mark a successful migration version. Extension enable/disable
behavior remains unchanged and never creates or deletes schema.

### 6.3 Baselines and future changes

1. **Core baseline:** define `runtime_extension_states`; a following Core
   migration creates the six health tables and indexes.
2. **ETF Grid baseline:** define only `etf_grid_*` tables inside the ETF Grid
   Extension.
3. **Mi Health baseline:** define only `mi_health_bindings` and
   `mi_health_qr_attempts` inside the Mi Health Extension.
4. Reviewed `CREATE TABLE IF NOT EXISTS`-equivalent baseline operations allow
   empty and existing databases to adopt migrations without altering existing
   rows. Schema-comparison tests must still prove that the resulting shape
   matches the current models.
5. Remove `metadata.create_all()` from Runtime extension-state initialization and
   both Extensions after their baselines are active. Do not move any Extension
   DDL into Core to achieve this.

SQLAlchemy models describe each module's current ORM shape; its local migrations
are the authoritative schema history. Future schema changes add explicit,
reviewed revisions in the owning module and preserve existing data unless the
migration explicitly states otherwise.

### 6.4 Migration verification

Test all of the following against real PostgreSQL:

- Empty databases reach Core, ETF Grid, and Mi Health heads independently with
  the expected schemas and separate version tables.
- Existing pre-v0.7.4 tables and rows remain intact during baseline adoption.
- Re-running Core startup or Extension registration at head performs no schema
  changes and is idempotent.
- Core migration files contain no Extension table definitions or imports.
- Concurrent execution within one namespace is serialized, while independent
  version histories cannot overwrite one another.
- Core migration failure prevents Extension loading; Extension migration failure
  prevents that Extension from completing registration.
- Extension registration performs no `create_all()` and works with Extensions
  enabled or disabled after local migration.
- Agno and Logto schemas are untouched.

## 7. Data Retention Map

| Data | Core table | Lifecycle | First adapter |
|------|------------|-----------|---------------|
| Existing Xiaomi credentials and binding state | `mi_health_bindings` | Channel-private current row; existing behavior | Mi Health Extension |
| Existing QR approval attempts | `mi_health_qr_attempts` | Channel-private transient state | Mi Health Extension |
| Height, limited demographic context, and goals | `health_profiles` | **Latest snapshot per owner and provider** | Mi Fitness Profile |
| Daily activity, HR, SpO2, and sleep summaries | `health_daily_summaries` | **History; one row per owner/provider/day** | Mi Fitness daily reports |
| Individual sleep sessions and raw stages | `health_sleep_sessions` | **History; upsert by provider record identity** | Mi Fitness raw sleep |
| Weight and core body composition | `health_body_measurements` | **History; upsert by provider record identity** | Mi Fitness raw weight |
| Workout summaries | `health_workouts` | **History; upsert by provider record identity** | Mi Fitness sport records |
| Backfill and incremental progress | `health_ingestion_states` | **Latest state per owner/provider/stream** | Core ingestion service |

`provider` is a stable server-assigned contract value. The initial value is
`mi_fitness`; it is never accepted from an LLM argument or request payload.
Provider-specific IDs and raw values are isolated in metadata/payload columns,
not propagated into canonical column names.

With one provider, daily data still appears as one row per user/day. With future
providers, the same table permits one row per provider/day. Cross-provider
merging is deliberately deferred; Core query services must not silently discard
one provider's contribution.

## 8. Core Health Database Design

### 8.1 Shared conventions

- Every health table includes `user_id String(128)` and `provider String(32)` in
  its primary key. There is no FK to `mi_health_bindings` or any other channel
  table.
- `user_id` comes only from verified request/run context. Logto remains the user
  authority; Runtime does not invent a local user FK for this milestone.
- `source_record_id Text` is a deterministic, versioned provider record key
  assigned by the adapter. Re-reading the same provider record produces the same
  key; random UUIDs are forbidden for source identity.
- For Mi Fitness, the adapter derives `source_record_id` from the reviewed
  composite natural keys (`sid`, outer record key where applicable, and source
  epoch). The original components remain in `provider_metadata`.
- `source_device_id Text` is an optional generic provenance field. For Mi
  Fitness it can carry `sid`; it is not asserted to be a friendly device name or
  a scale user/account ID.
- Query-friendly instants use `DateTime(timezone=True)`. Provider epoch values
  and versions can remain in `provider_metadata` without imposing that transport
  shape on Core.
- `Date` fields represent the local health day, not the UTC date of an arbitrary
  instant.
- Mass and percentage columns use `Numeric`; counts, durations, BPM, SpO2, and
  calories use integer types. Do not use binary floats for normalized storage.
- `provider_metadata` and `raw_payload` use PostgreSQL `JSONB`. They contain
  private health data and must never appear in logs or exceptions.
- `created_at`, `updated_at`, and `synced_at` are distinct local timestamps.
- Core ingestion supplies generic upsert and `delete_provider_data()` operations.
  Channel code never issues arbitrary SQL against Core tables.

### 8.2 `health_profiles` — latest provider snapshot

Primary key: `(user_id, provider)`. Each provider has at most one current profile
per owner. A successful sync updates supplied canonical fields; absent fields do
not erase values learned previously. Full raw Profile is not stored.

| Column | Type | Null | Meaning |
|--------|------|------|---------|
| `user_id` | `String(128)` | No | PK; verified Runtime owner |
| `provider` | `String(32)` | No | PK; contributing provider |
| `height_cm` | `Numeric(5,2)` | Yes | Current height |
| `birth_year` | `Integer` | Yes | Year only; no full birth date |
| `sex` | `String(16)` | Yes | Optional canonical context; no invented mapping |
| `daily_step_goal` | `Integer` | Yes | Current daily step goal |
| `daily_calorie_goal_kcal` | `Integer` | Yes | Current daily calorie goal |
| `stand_goal` | `Integer` | Yes | Current stand/activity-count goal |
| `activity_goal_minutes` | `Integer` | Yes | Current activity-time goal |
| `provider_metadata` | `JSONB` | No | Non-sensitive provenance; no account identifiers |
| `synced_at` | `DateTime(timezone=True)` | No | Last successful provider read |
| `created_at` | `DateTime(timezone=True)` | No | Local creation time |
| `updated_at` | `DateTime(timezone=True)` | No | Local last-change time |

Do not store name, full birth date, current profile weight, account identifiers,
icons, medals, device IDs, or raw Profile JSON. Current weight comes from valid
body-measurement history.

breakdown was provided.

| `last_run_started_at` | `DateTime(timezone=True)` | Yes | Latest attempt start |
| `last_succeeded_at` | `DateTime(timezone=True)` | Yes | Latest successful completion |
| `last_failed_at` | `DateTime(timezone=True)` | Yes | Latest failed completion |
| `consecutive_failures` | `Integer` | No | Reset after success; default `0` |
| `last_error_code` | `String(64)` | Yes | Safe typed error only |
| `revision` | `Integer` | No | Optimistic concurrency guard; default `0` |
| `created_at` | `DateTime(timezone=True)` | No | Local creation time |
| `updated_at` | `DateTime(timezone=True)` | No | Local last-change time |

Do not store provider page cursors, credentials, raw responses, health values, or
provider error bodies. The checkpoint advances only after every page in the
window has committed.

## 9. Provider Mapping and Synchronization

1. Mi Health supplies `provider="mi_fitness"` internally and maps Xiaomi fields
   into Core contracts. Core ingestion remains provider-neutral.
2. The initial milestone exposes an owner-triggered sync entrypoint. It does not
   enumerate bindings or add a background schedule.
3. Reuse the existing bounded session renewal and one-retry behavior. Startup
   migration and Extension registration perform no provider request.
4. Backfill each stream in bounded reverse windows. Incremental reads overlap the
   previous successful window to catch corrections. Raw Mi Fitness reads apply
   the documented first-bucket margin and local inclusive filtering.
5. Follow provider page cursors only in memory, reject missing/repeated cursors,
   cap pages, and never treat a truncated window as successful.
6. Commit each complete window atomically with its ingestion checkpoint. Streams
   report independent safe outcomes.
7. Upsert canonical records by their declared keys. Identical replays are no-ops;
   corrections update canonical fields, provenance, raw payload, and `synced_at`
   while preserving `created_at`.
8. Explicit provider deletion marks `is_deleted=true`; ordinary reads exclude
   tombstones. A missing row in a bounded response is not proof of deletion.
9. Daily metrics merge into the same owner/provider/day row without erasing
   metrics absent from the current stream.
10. All operations are idempotent and safe after network, provider, process, or
    database failure.

## 10. Provider Unlink and Data Lifecycle

Core health rows have no channel-table FK. Explicit Mi Health unbinding instead
uses one transaction to:

1. Delete `health_ingestion_states` for the current owner and
   `provider="mi_fitness"`.
2. Delete Mi Fitness rows from the five health data tables for that owner.
3. Delete the owner's Mi Health binding and QR attempts.

The Core cleanup repository participates in the same SQLAlchemy session as the
binding deletion; independent sessions are not acceptable for this composite
operation. Any failure rolls back the whole unbind.

This provider-scoped deletion preserves rows from every other provider and
prevents a later different Xiaomi account from mixing with the previous
account's history. Reauthentication or session renewal without unbinding does
not delete health data. Disabling Mi Health disables operations without deleting
credentials or health history.

The unbind confirmation must disclose the provider-data deletion. A future
independent Core health deletion flow can address retention without unlinking a
channel; it is not part of this milestone.

## 11. Security and Privacy Requirements

- Add two-user tests for every Core repository, adapter service, migration-era
  startup path, and real database read/write.
- Administrator identity remains self-scoped and grants no cross-user health
  access.
- Health values and raw JSONB payloads are private data, not operational logs.
  Log only event names, provider/stream names, counts, safe errors, trace IDs,
  and permitted Runtime user IDs.
- Synthetic tests cover credential and health-value sentinel redaction from
  logs, exceptions, API responses, migration output, and sync summaries.
- Live measurements remain only in the owner-approved local environment and are
  never copied into fixtures, plans, commits, or screenshots.
- Sync responses return counts and safe state only. No public endpoint dumps
  `raw_payload`.
- Extension-disabled operations stop before provider calls or business writes.
- Core and Extension-local migrations contain schema and synthetic structural
  operations only, never real health or account data.
