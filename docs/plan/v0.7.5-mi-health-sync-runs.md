## 2. Context

Runtime already implements bounded Mi Fitness backfill and incremental sync through
`POST /api/v1/extensions/mi-health/sync`. The endpoint waits for all streams and
returns only the final stream list. A browser refresh, network interruption, or
future scheduled execution therefore cannot be represented as one consistent
synchronization run.

Core already persists `health_ingestion_states` for each owner, provider, and
stream. Those rows are checkpoints and current stream-health state: they control
overlap, backfill completion, optimistic revisions, and the latest safe success or
failure. They do not identify a complete run or preserve the outcome of each stream
within that run.

This milestone adds a Mi Health-owned run record while leaving Core health data and
checkpoint semantics intact. Manual synchronization is the only trigger implemented
here, but the run model and execution service must accept scheduled execution later
without a schema or product-contract rewrite.

Read first: `AGENTS.md`, `docs/plan/v0.7.4-personal-health-data.md`,
`docs/architecture/system-architecture.md`,
`src/spectres/extensions/mi_health/service/sync.py`, and
`src/spectres/health/ingestion.py`.

## 3. Confirmed Design Decisions

1. **One Extension-owned run table.** Add `mi_health_sync_runs`; do not add a
   separate run-stream table. Store the fixed, small set of stream outcomes as a
   typed JSONB snapshot on each run.
2. **Runs and checkpoints remain separate.** A run describes one execution;
   `health_ingestion_states` continues to describe durable stream progress and
   current health. Neither model replaces the other.
3. **One active run per owner.** Manual and future scheduled triggers share the
   same active-run constraint and checkpoint writer. Different users remain
   independent.
4. **The run is authoritative.** `queued`, `running`, terminal status, stream
   outcomes, counts, timestamps, trigger source, and safe failures come from the
   database rather than browser-local request state.
5. **Manual sync returns before completion.** `POST /sync` creates and returns a
   `202` run snapshot, then executes through a Runtime-owned background task.
   Clients observe the run through `GET /sync/status`.
6. **No global read/write pipeline.** Each stream continues to read, map, and
   atomically write bounded windows. The public UI represents one run, not two
   independent cloud-read and database-write operations.
7. **Future schedules reuse this service.** A later personal Schedule targets a Mi
   Health Workflow whose verified `RunContext.user_id` enters the same run service.
   This milestone adds no Workflow, Schedule, scheduler, or personal-task seeding.
8. **Ordinary-user self-scope only.** No administrator cross-user run view,
   ownerOverride, user query parameter, or payload-supplied identity is added.
9. **No health values in run state.** Run rows contain operational metadata only:
   no raw provider payloads, measurements, Profile values, account identifiers,
   credentials, pagination cursors, or provider error bodies.
10. **Coordinated API revision.** `POST /sync` changes from a synchronous `200`
    stream-result response to `202` with a run snapshot. The Web Client currently
    has no sync caller; Runtime and Web Client v0.5.4 adopt the new contract
    together rather than retaining a second manual sync entrypoint.

## 4. Scope

### 4.1 In Scope

1. Add the Mi Health run model, typed stream snapshot, local Alembic migration,
   indexes, and one-active-run database invariant.
2. Add an owner-scoped run service that creates, starts, advances, completes, and
   queries runs using the Extension composition root's shared session factory.
3. Refactor the existing sync orchestration so every manual execution updates one
   run and its JSONB stream outcomes while preserving bounded windows, pagination,
   renewal/retry, idempotent ingestion, and independent stream failures.
4. Replace the long-waiting manual response with `202 Accepted` and a safe run
   snapshot; execute the committed run after the response through FastAPI/ASGI
   background execution without adding a dependency or custom scheduler.
5. Add `GET /sync/status` with the active run, latest run, and current stream
   checkpoint state. Status reads never contact Xiaomi.
6. Reconcile `queued` or `running` rows left by process termination as
   `interrupted` during Extension registration before traffic is accepted.
7. Reject unbinding while a run is active, and delete terminal/interrupted/skipped
   run history during confirmed unbinding together with the owner's other Mi
   Health state. Extension disablement preserves runs and data.
8. Add safe API errors and mappings for active-run conflicts, authentication,
   missing bindings, provider failures, credential protection, and disabled
   Extensions.
9. Add unit, real-PostgreSQL, privacy, concurrency, migration, and two-user
   isolation coverage; update living architecture and project guidance when the
   behavior lands.
10. Set the package version to `0.7.5` only when the milestone is released.

### 4.2 Out of Scope

- Creating, updating, enabling, disabling, or triggering Mi Health Schedules.
- A Mi Health Workflow, automatic personal Schedule creation, catch-up policy, or
  cross-user scheduled fan-out.
- A general job queue, distributed worker protocol, custom scheduler, or parallel
  schedule-management API.
- Full run-history pagination, run deletion APIs, retention policies, cancellation,
  or per-stream manual retry.
- Parallel execution of streams within a run.
- Health metric, Profile-field, workout, sleep, weight, or other personal-value
  responses; those belong to separate Core health query contracts and pages.
- Administrator access to user bindings, runs, checkpoints, or health data.
- Changes to canonical health models, provider mappings, supported streams, or
  backfill duration except where run instrumentation requires safe error metadata.

## 5. Persistence Model

### 5.1 `mi_health_sync_runs`

Add the model to `src/spectres/extensions/mi_health/models.py` and a new
Extension-local migration after `0001_mi_health_baseline`.

| Column | Type | Required | Meaning |
|--------|------|----------|---------|
| `id` | `String(36)` | PK | Server-generated UUID for one run |
| `user_id` | `String(128)` | Yes | Verified owner; never accepted from a payload |
| `trigger_type` | `String(16)` | Yes | `manual` now; `scheduled` supported by the contract |
| `status` | `String(32)` | Yes | `queued`, `running`, `succeeded`, `partially_failed`, `failed`, `interrupted`, or `skipped` |
| `streams` | `JSONB` | Yes | Ordered list of safe per-stream run snapshots |
| `error_code` | `String(64)` | No | Safe run-level failure or skip reason only |
| `schedule_run_id` | `String(128)` | No | Reserved correlation for a future native scheduled run |
| `created_at` | `DateTime(timezone=True)` | Yes | Run creation time |
| `started_at` | `DateTime(timezone=True)` | No | Execution start time |
| `finished_at` | `DateTime(timezone=True)` | No | Terminal completion time |
| `updated_at` | `DateTime(timezone=True)` | Yes | Last persisted run change |

Add:

- An index on `(user_id, created_at)` for active/latest owner queries.
- A PostgreSQL partial unique index on `user_id` for statuses `queued` and
  `running`, enforcing at most one active run per owner across competing requests.
- Database checks for non-empty trigger/status values where consistent with the
  existing migration style; application services and typed contracts enforce the
  complete state machine and JSONB shape.

Do not add a foreign key into Agno-managed schedule tables. `schedule_run_id` is an
optional correlation value, not ownership or an execution dependency.

### 5.2 JSONB stream snapshot

The service owns a typed internal representation with these fields:

| Field | Type | Meaning |
|-------|------|---------|
| `stream` | string | One stable internal stream id from the existing fixed stream list |
| `status` | string | `pending`, `running`, `succeeded`, `failed`, or `skipped` |
| `record_count` | non-negative integer | Records processed/upserted, not necessarily newly created |
| `failure_stage` | string or null | `provider_read`, `record_mapping`, `database_write`, `checkpoint_conflict`, or `authentication`; unknown failures use null |
| `error_code` | string or null | Existing safe machine-readable code; never exception text |
| `started_at` | datetime or null | Stream execution start |
| `finished_at` | datetime or null | Stream terminal completion |

Initialize a manual run with all supported streams in stable `_STREAMS` order and
`pending` status. Persist the complete typed snapshot on each stream transition.
The current single-writer service updates one run row; do not introduce unvalidated
arbitrary JSON writes or public JSON patch operations.

### 5.3 Relationship to Core checkpoints

Continue using `HealthIngestionService` for all checkpoint and health writes. Add a
provider-scoped checkpoint-list query only if needed by the status composer; Mi
Health must not issue direct SQL against Core-owned tables.

`GET /sync/status` exposes each supported stream even when no checkpoint exists:

```text
stream
status             never_synced | succeeded | failed
last_run_started_at
last_succeeded_at
last_failed_at
last_successful_window_end
backfill_completed
last_error_code
```

This current stream state is independent of the active/latest run snapshot.
`last_successful_window_end` is the end of the last successfully committed data
window, not an operation timestamp. Do not infer a historical run result by
combining checkpoint timestamps.

## 6. Run Lifecycle and Execution

### 6.1 Creation and background execution

Refactor `MiHealthSyncService` or introduce a focused Mi Health run service in the
same Extension service layer. The composition root constructs one shared instance
and injects it into the router and binding service where active-run checks are
needed. Preserve thin API adapters and explicit session ownership.

Manual start performs the following:

1. Derive `user_id` through `require_user_id`.
2. Require an existing binding; a locally known `reauth_required` binding returns
   `authentication_required` without contacting Xiaomi.
3. Atomically insert a `queued` run with all pending stream snapshots.
4. Return `202` and the safe run snapshot.
5. After the response, execute the committed run by its server-generated id through
   a FastAPI background task. Execution reloads the run and owner from Runtime
   state; it does not trust client fields.

The background executor catches all expected operational failures and persists a
terminal run state. It never logs credentials, raw provider responses, health
values, or unhandled exception bodies as public errors.

### 6.2 Stream and run completion

- Mark the run `running` and set `started_at` before provider work.
- Mark one stream `running`, execute the existing bounded sync logic, then persist
  its terminal snapshot before advancing to the next stream.
- Preserve at most one renewal and retry per stream and the existing independent
  stream failure behavior.
- Distinguish safe failure stages where the existing exception boundary proves the
  stage. Do not guess that every unknown exception was a database failure.
- Set `succeeded` only when every stream succeeds, `partially_failed` when at
  least one succeeds and at least one fails, and `failed` when no stream succeeds
  or a run-level failure prevents useful work.
- Set `finished_at` exactly once for every terminal state.
- Keep the existing binding updates: authenticated provider success may mark the
  binding authenticated; terminal authentication failure may require QR
  reauthorization. A status response must reflect the latest persisted binding on
  the next existing `GET /status` call.

A successful window still commits health records and its Core checkpoint before
the run-stream snapshot is updated. A later run-status write failure must not be
misrepresented as a failed health window or cause a second provider mutation
retry within the same execution.

### 6.3 Concurrency, disablement, and shutdown

- Competing manual starts rely on the partial unique index, not only a Python
  in-memory lock. Return `409 sync_in_progress`; the Client refreshes status to
  discover the authoritative active run.
- A disabled Extension blocks new REST work through the existing activation guard.
  Disabling does not claim to cancel an already running operation and preserves all
  run and health state.
- Browser disconnect or fetch abort does not cancel Runtime execution.
- On registration in the single-process deployment, convert leftover `queued` and
  `running` runs to `interrupted` with a safe error code and `finished_at`. A user
  can explicitly start a new run afterward; checkpoints keep the retry idempotent.
- Do not mark terminal runs as active and do not automatically retry interrupted
  runs.

### 6.4 Unbinding

Unbinding during `queued` or `running` returns `409 sync_in_progress`; this
milestone does not add cancellation. Once no run is active, unbinding atomically
deletes the owner's binding, QR attempts, Mi Fitness health contribution,
checkpoints, and Mi Health run history. Another owner's rows and other providers
remain untouched.

## 7. Public HTTP Contract

Base path remains `/api/v1/extensions/mi-health`. Existing binding, QR, session,
and unbind response shapes remain unchanged except for the new active-sync unbind
error.

### 7.1 Start manual synchronization

```http
POST /sync
202 Accepted
```

Response: `SyncRunResponse`.

```json
{
  "id": "server-generated-uuid",
  "trigger_type": "manual",
  "status": "queued",
  "streams": [
    {
      "stream": "profile",
      "status": "pending",
      "record_count": 0,
      "failure_stage": null,
      "error_code": null,
      "started_at": null,
      "finished_at": null
    }
  ],
  "error_code": null,
  "created_at": "2026-11-17T08:00:00Z",
  "started_at": null,
  "finished_at": null
}
```

The actual response contains every supported stream. It contains no owner id,
schedule id, health values, account fields, or credentials.

Relevant errors:

- `404 not_bound`
- `409 authentication_required`
- `409 sync_in_progress`
- `403 extension_disabled`
- Existing authentication, credential-protection, and validation errors where
  applicable

### 7.2 Read synchronization status

```http
GET /sync/status
200 OK
```

Response: `SyncStatusResponse`.

```json
{
  "active_run": null,
  "last_run": {
    "id": "server-generated-uuid",
    "trigger_type": "manual",
    "status": "partially_failed",
    "streams": [],
    "error_code": null,
    "created_at": "2026-11-17T08:00:00Z",
    "started_at": "2026-11-17T08:00:00Z",
    "finished_at": "2026-11-17T08:01:00Z"
  },
  "streams": [
    {
      "stream": "profile",
      "status": "succeeded",
      "last_run_started_at": "2026-11-17T08:00:00Z",
      "last_succeeded_at": "2026-11-17T08:00:02Z",
      "last_failed_at": null,
      "last_successful_window_end": "2026-11-17T08:00:02Z",
      "backfill_completed": true,
      "last_error_code": null
    }
  ]
}
```

`active_run` is the owner's `queued` or `running` row. `last_run` is the latest
non-active run, including `interrupted` or `skipped`, independently of whether an
active run exists. With no runs, both are null. `streams` always describes all
currently supported streams and uses `never_synced` when no checkpoint exists.

This route is local-only and makes no Xiaomi request. A future scheduled trigger
uses the same schemas with `trigger_type=scheduled`; no parallel status API is
needed.

## 8. Security and Ownership

- Every public read and mutation derives the owner from verified request context.
- Background execution loads the owner from a server-created run, never from task
  payload overrides.
- Future Workflow execution must require verified `RunContext.user_id` and fail
  closed when absent; this is a design constraint, not implemented behavior in
  v0.7.5.
- All run and checkpoint queries include the verified owner. Cross-user run ids and
  status requests reveal nothing and require no administrator exception.
- Administrator mode retains global Extension activation only; do not add a
  cross-user run listing or health/synchronization status endpoint.
- Run JSONB and API responses contain only the fields declared above. Add privacy
  sentinels to tests for provider payloads, health values, tokens, account ids, and
  exception text.
- `record_count` is operational metadata and never includes record contents.
