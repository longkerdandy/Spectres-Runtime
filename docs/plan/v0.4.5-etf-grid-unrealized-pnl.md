# v0.4.5 — etf_grid Unrealized P&L in Portfolio Status

| Field | Value |
|-------|-------|
| **Status** | completed |
| **Created** | 2026-10-13 |
| **Goal** | Expose per-symbol unrealized (floating) P&L — amount and percent — in `get_portfolio_status`, so the web client's grid status table can show holding P&L with an authoritative, ledger-consistent calculation. |

---

## 1. Background

The web client's v0.2.0 grid status page shows each symbol's holdings,
average cost, market value, and **realized** P&L — but not the floating
P&L of the current position, which is the number the owner actually
watches day to day.

The raw ingredients (`shares`, `avg_cost`, `close`, `market_value`) are
already in the `GET /status` response, so the client *could* derive it.
That was explicitly rejected: the client layer carries no business logic
(web-client AGENTS.md §3.3), and P&L conventions must have exactly one
authoritative definition — the Runtime's ledger math. This milestone adds
the derivation at the source.

Read first: `docs/plan/v0.4.0-etf-grid-extension-core.md` (ledger math),
`docs/plan/v0.4.1-etf-grid-api-tools.md` (status endpoint),
`docs/plan/v0.4.4-etf-grid-api-hardening.md` (REST contract conventions).

Prior dependencies: v0.4.1 (endpoint exists). No breaking change — the
response gains two fields; existing consumers are unaffected.

Key constraints:

- **Ledger-consistent definition**: unrealized P&L reuses the ledger's
  existing cost-basis convention (`position.avg_cost`), whatever it
  includes — this milestone must not redefine cost basis.
  - `unrealized = close × shares − avg_cost × shares`
    (equivalently `market_value − avg_cost × shares`)
  - `unrealized_percent = unrealized / (avg_cost × shares)`, a fraction
    like `gate_percentile` (0.12 = 12%), not a 0–100 number.
- **Null semantics**: both fields are `null` when the derivation is
  undefined — no position (`shares == 0` / no `avg_cost`), or no latest
  close. Never emit a fabricated zero.
- **Thin adapter unchanged**: the math lands in
  `service.get_portfolio_status` (the domain boundary); `api.py` stays
  a pass-through, and `to_jsonable` already stringifies Decimals.
- **Toolkit flows through automatically**: `get_grid_status` calls the
  same service, so the chat side gains the two fields with zero toolkit
  changes. That is intended, not scope creep.

## 2. Current State

- `etf_grid/service.py` `get_portfolio_status`: per symbol, emits
  `symbol`, `name`, `shares`, `avg_cost`, `realized`, `close`,
  `close_date`, `market_value` (`close × position.shares`), and the
  nested `signal` snapshot. Positions come from
  `ledger_service.get_positions()`.
- Tests: `tests/test_etf_grid_service.py` (service level) and
  `tests/test_etf_grid_api.py` (endpoint level) cover the current fields.

## 3. Scope

### 3.1 In Scope

1. **Unrealized P&L derivation** in `get_portfolio_status`
   - New fields per symbol row: `unrealized: Decimal | None` and
     `unrealized_percent: Decimal | None` (fraction).
   - Computed only when `position` exists, `shares > 0`, `avg_cost` is
     present, and `close` is present; otherwise both are `null`.
   - Decimal math throughout; no floats.

2. **Tests**
   - Service-level: derivation correctness (profit and loss cases), and
     all null branches (no position, no close, zero cost basis).
   - API-level: `GET /status` rows carry the two fields (stringified).

3. **Docs & versioning**
   - `runtime-extensions.md` §7 REST contract: document the two new
     fields and their null semantics.
   - Bump `pyproject.toml` `version` to `0.4.5` (per-milestone bump
     convention established in v0.4.4).

### 3.2 Out of Scope

- **Dividend/-split adjustments to cost basis** — the ledger's existing
  convention is reused as-is; any change to it is a domain milestone of
  its own.
- **Web client rendering** — the status-table column lands in the client
  repo as part of its v0.2.0 polish (separate change).
- **Realized P&L or signal semantics changes** — untouched.
- **P&L history / equity curve** — a future charting milestone on the
  client side; no time series is added here.
