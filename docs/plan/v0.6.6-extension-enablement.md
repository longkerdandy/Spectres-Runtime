## 1. Background

Runtime currently discovers trusted in-tree Extensions at startup. Presence in
the source tree is the only opt-in, and Runtime has no administrator-controlled
Extension activation state.

ADR 0012 confirms that static discovery remains appropriate for built-in
Extensions. Their Runtime code continues to ship with the Runtime project. Edge
services use a separate independent-deployment model and are not part of this
milestone.

Extension enablement must be a server-enforced operational state. Disabling an
Extension must prevent new REST, AI tool, Workflow, and scheduled business
operations while preserving its code, data, configuration, and Schedules for
later re-enablement.

## 2. Confirmed Decisions

1. **Discovery and registration remain static.** Every trusted Extension is
   discovered and registered with Runtime even when its persisted state is
   disabled. Startup remains fail-loud for broken built-in code.
2. **Activation is independent of registration.** Routers, Toolkits, Workflows,
   and Schedules remain registered, but each execution boundary checks the
   persisted Extension state before business work begins.
3. **Runtime is authoritative.** Every caller, including an administrator or
   internal service, is subject to the disabled state at Extension execution
   boundaries.
4. **State is global, not per-user.** One Extension state applies to every user.
   Per-user feature flags and subscriptions are not introduced.
5. **Disable is not uninstall.** Existing tables, data, configuration, and
   Schedules are retained. Already-running operations are not forcibly killed.
6. **No restart is required.** AgentOS component lists are not dynamically
   rebuilt when an administrator changes a state.
7. **Existing Extensions remain enabled by default.** Startup inserts missing
   state rows additively and never overwrites an administrator's stored choice.

## 3. Runtime Design

### 3.1 Preserve Extension identity after discovery

Add a small loaded-extension record in `extensions/base.py`, conceptually:

```text
LoadedExtension
  id: str
  name: str
  description: str
  contribution: ExtensionContribution
```

Each manifest declares a stable snake_case `id` and non-empty human-readable
`name` and `description`. The id keys state and administration; display metadata
comes from discovered code. No separate Extension version is needed because the
code releases with Runtime.

Change `load_extensions()` to return these records. Update assembly and schedule
registration to consume the flattened contribution while retaining the owning
Extension id for mounting, guards, catalog output, logs, and audits.

Do not add a class hierarchy, dependency-injection framework, dynamic package
installation, or a new lifecycle hook system.

### 3.2 Persistent state and service

Add a core-owned `runtime_extension_states` table using the shared PostgreSQL
engine:

| Column | Type | Notes |
|--------|------|-------|
| `name` | String PK | Stable snake_case Extension id from the discovered manifest |
| `enabled` | Boolean NOT NULL | Global activation state |
| `updated_by` | String(128) NULL | Last administrator JWT subject; NULL for bootstrap |
| `created_at` | DateTime(tz) NOT NULL | Row creation time |
| `updated_at` | DateTime(tz) NOT NULL | Last state change |

This is an additive schema rollout: `create_all()` can create the new table
without changing existing Extension tables. No database reset or Alembic
adoption is required.

Add a core Extension state service that:

- Reconciles newly discovered Extension ids with `enabled=true` by default.
- Preserves existing rows and their state across restarts.
- Does not expose stale rows for code that is no longer discovered as a current
  manageable Extension.
- Returns current state for every discovered Extension.
- Applies idempotent administrator enable/disable updates and returns the new
  state.
- Emits an audit event containing Extension id, administrator subject, previous
  state, and new state, without secrets.

Use the database as the immediate source of truth. Do not add a process-local
state cache in this milestone; administrator changes must not become stale in a
second Runtime process.

### 3.3 Catalog and administration API

Add core routes under `/api/v1`:

| Method | Path | Access | Behavior |
|--------|------|--------|----------|
| GET | `/extensions` | Authenticated user | Return every currently discovered Extension's id, display metadata, and enabled state |
| PATCH | `/extensions/{extension_id}` | `agent_os:admin` | Set `enabled` and return the same metadata/state contract |

Example catalog response:

```json
{
  "items": [
    {
      "id": "etf_grid",
      "name": "ETF Grid",
      "description": "ETF grid trading status, trade ledger, signals, and scheduled data workflows.",
      "enabled": true,
      "updated_at": "2026-11-07T10:00:00Z"
    }
  ]
}
```

The PATCH body contains only `enabled`. Unknown or no-longer-discovered ids
return 404. Ordinary users receive 403 for PATCH. Validation failures retain
FastAPI's structured 422 response. State changes use the verified administrator
identity from `request.state.user_id`; no administrator or owner id is accepted
from the request body.

These are core management routes and are never guarded by the state of the
Extension being managed. No new Runtime role or Logto scope is required beyond
`agent_os:admin`.

### 3.4 REST execution guard

Mount each Extension router with its owning Extension id and a shared FastAPI
guard. A disabled Extension returns HTTP 403 with a stable structured
`extension_disabled` error before the route's business service executes.

The guard applies to normal, administrator, and internal-service calls to that
Extension. It does not apply to the core Extension catalog/management routes or
to unrelated core APIs.

Do not duplicate hand-written state checks in every ETF Grid endpoint. If an
existing Extension router has a separate internal operational route, it remains
subject to the same disabled state.

### 3.5 Toolkit execution guard

Keep all built-in Toolkits attached to the Team Leader. Add a shared guard at
the Toolkit/tool execution boundary rather than relying on every domain method
to remember a check.

The guard must preserve:

- Existing tool names and input schemas.
- `RunContext` injection and current-user ownership behavior.
- The existing `{ok, data}` / `{ok, error}` tool-result envelope.
- Tool ordering and registration behavior.

A disabled tool returns `{ok: false}` with error type `extension_disabled` and
performs no business read, write, external request, or Edge call. Tool definitions
may remain visible to the model; execution is the mandatory enforcement point.

Before choosing the wrapper implementation, verify it against the pinned Agno
Toolkit execution path, including synchronous and asynchronous functions and
injected run-context parameters. Do not change the LLM-visible signatures merely
to make wrapping easier.

### 3.6 Workflow and scheduled execution guard

Keep Extension Workflows registered with their existing stable ids. Add an
owning-Extension guard before the first business step or side effect.

For a disabled Extension:

- No external data request, database mutation, signal computation, or Edge call
  occurs.
- The Workflow returns a structured disabled/skip result naming the Extension.
- The result is non-retryable and is not presented as a transient provider or
  infrastructure failure.

Current workflow-backed system and personal Schedules remain registered and
retain their own enabled state, cron, target, owner, retry policy, and history.
Do not delete, disable, re-enable, or otherwise rewrite them when the Extension
state changes.

A schedule that fires while its Extension is disabled may record the disabled
result. Verify that this path does not trigger automatic retries. No separate
Extension-aware scheduler, parallel schedule API, or schedule provenance layer is
introduced.

### 3.7 Disable/enable semantics

A disable operation:

- Immediately prevents new business operations at all guarded boundaries.
- Does not terminate an already-running REST request, tool call, Workflow, or
  external synchronization.
- Does not delete or hide historical Runtime data through direct database
  changes.
- Does not modify native Schedule configuration.

An enable operation restores normal execution using the existing code and stored
configuration. No bootstrap data is duplicated when an Extension is re-enabled.

## 4. Scope

### 4.1 In Scope

1. Preserve loaded Extension ids alongside their contributions throughout
   Runtime assembly.
2. Add the core Extension state table, additive startup reconciliation, state
   service, and administrator audit events.
3. Add authenticated catalog and admin-only state-change APIs.
4. Enforce disabled state at Extension Router, Toolkit, and Workflow execution
   boundaries.
5. Verify disabled workflow-backed Schedules have no business side effects and
   do not enter transient-failure retries.
6. Add unit and real-PostgreSQL coverage, update living Runtime documentation,
   and run standard Runtime quality gates plus a live JWT API/execution
   walkthrough.

### 4.2 Out of Scope

- All Web Client implementation, including catalog consumption, navigation or
  tool-card filtering, administrator screens, and frontend quality checks.
- The `xiaomi_health` Runtime Extension, Edge service, Edge API client, event
  receiver, or any Edge-specific database tables.
- Module Federation, the Edge UI Host, remote catalogs, dynamic Edge UI loading,
  or independent frontend releases.
- Dynamic Extension installation, upload, uninstall, out-of-tree discovery, or
  per-user enablement.
- A generic Edge control plane, Connector abstraction, Edge registry, ingestion
  protocol, or custom scheduler.
- Runtime or Edge BFF browser sessions and changes to Logto authentication.
- Deleting Extension data, cancelling in-flight work, or automatically changing
  native Schedule enabled state when an Extension is toggled.
- Dynamic removal of disabled tools or Workflows from AgentOS catalogs.

## 5. Success Criteria

- [x] All existing and newly discovered Extensions receive additive state rows;
  existing Extensions remain enabled after upgrade, and restarts preserve admin
  choices without duplicate bootstrap effects.
- [x] Any authenticated user can read the current Extension catalog. Only
  `agent_os:admin` can change state; unknown ids, invalid bodies, and ordinary
  admin attempts retain documented 404/422/403 behavior.
- [x] Disabling ETF Grid immediately blocks its REST endpoints with a stable
  `extension_disabled` response and prevents route business services from
  running for ordinary, administrator, and internal callers.
- [x] Disabled ETF Grid tools preserve their public names/schemas and return the
  standard structured error without reads, writes, provider calls, or ownership
  changes.
- [x] Disabled ETF Grid Workflows stop before business side effects. System and
  personal Schedules retain their configuration and do not retry a disabled
  result as a transient failure.
- [x] Disabling an Extension does not delete data, kill an in-flight operation,
  or modify Schedule ownership/configuration; re-enabling restores execution
  without a Runtime restart.
- [x] ETF Grid private-data isolation, native authorization, AG-UI behavior, and
  existing scheduler/Extension regression tests remain green.
- [x] Runtime Ruff lint, formatting, strict Mypy, default pytest, and relevant
  real-PostgreSQL tests pass; the live two-role API/execution walkthrough
  succeeds.
