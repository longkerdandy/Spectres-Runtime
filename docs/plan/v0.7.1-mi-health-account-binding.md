# v0.7.1 — Mi Health Account Binding and Session Lifecycle

| Field | Value |
|-------|-------|
| **Status** | review |
| **Created** | 2026-11-10 |
| **Goal** | Deliver the built-in Mi Health Runtime Extension with owner-scoped QR account binding, encrypted credential persistence, bounded session renewal, and a read-only Profile connectivity check. |
| **Milestone** | v0.7.1 |
| **Client counterpart** | Web Client v0.5.0 |

---

## 1. Background

Runtime v0.7.0 completed the transition from the obsolete independent Mi Health
Edge topology to a trusted built-in Runtime and Web Client Extension. The old
Edge-specific Logto resource, role, scope, and JWT audience have been removed;
reusable protocol research is preserved under `docs/research/mi-health/`.

The research establishes an initial QR-only authentication contract for the
China region. One owner-approved QR login and one proactive `passToken` renewal
succeeded in a disposable standalone harness. Production authentication,
credential persistence, and long-term unattended reliability are not implemented
or established by that research.

This milestone turns the validated authentication path into a production Runtime
vertical slice. It deliberately stops before health-data persistence and
synchronization. The corresponding Web Client milestone supplies the QR approval
and binding-management UI.

## 2. Confirmed Decisions

1. **Use the built-in Extension contract.** The Runtime id is `mi_health`; code
   lives under `src/spectres/extensions/mi_health/`, and routes use
   `/api/v1/extensions/mi-health/`. Core must not import Extension code.
2. **One Xiaomi account per Runtime user.** A user has at most one current Mi
   Health binding. Reauthentication replaces that owner's binding; binding a
   different account first requires explicit unbinding.
3. **China only.** `MI_HEALTH_REGION` must be configured explicitly and the
   initial implementation accepts only `cn`. Do not discover, infer, or silently
   default another account region.
4. **QR and `passToken` renewal only.** Password login, password recovery, and
   standalone SMS login are excluded. Long-term credential failure returns the
   owner to QR authorization.
5. **Protect all authentication material.** Encrypt retained credentials and
   transient polling URLs at rest. Keep the encryption key outside PostgreSQL.
   Never log or commit tokens, secrets, QR payloads, complete sensitive URLs, or
   Xiaomi account identifiers.
6. **Persist attempts, not process-local authority.** QR attempts and bindings
   are owner-scoped PostgreSQL state. Sensitive `lp` material exists only for an
   active attempt and is deleted when that attempt completes, is cancelled, is
   superseded, or expires.
7. **Bounded renewal and retry.** Reuse an existing health session first. After
   a known-valid signed health request receives HTTP 401, renew at most once,
   perform STS, and retry once with a fresh nonce. A second 401 is a failure.
8. **Atomic session rotation.** Persist new `serviceToken` and `ssecurity`
   together only after renewal, STS, and required-field validation succeed.
   Retain the old session on failure; rotate `passToken` in the same transaction
   if Xiaomi ever supplies a replacement.
9. **Profile is a connectivity check only.** Use the existing Profile API to
   prove that the session can perform a signed health read. Do not persist a
   Profile response or expose unnecessary personal fields.
10. **No automation or agent surface yet.** This milestone contributes one REST
    router and no Toolkit, Workflow, or Schedule. Startup performs no network
    calls and registration remains idempotent.
11. **Use the existing Runtime identity and activation model.** Every operation
    derives its owner from `request.state.user_id`; internal-service identity and
    administrator scope do not grant cross-user access. No Mi Health Logto
    resource, role, permission, or token is introduced.

## 3. Scope

### 3.1 In Scope

1. Add the statically discovered `mi_health` Extension registration module, configuration,
   composition root, SQLAlchemy models, services, typed HTTP schemas, and router.
2. Add explicit `MI_HEALTH_*` configuration to both complete environment sets in
   `.env.example`, with non-secret development and test placeholders.
3. Implement owner-scoped QR challenge creation, one bounded long-poll, cancel,
   supersession, and terminal-state cleanup.
4. Implement QR result parsing, STS exchange, initial binding creation, and
   replacement after reauthentication.
5. Implement encrypted credential storage, stable `deviceId` handling, explicit
   unbinding, and non-sensitive binding status.
6. Implement explicit proactive renewal and Profile verification with bounded
   automatic renewal/retry on a valid-session HTTP 401.
7. Reuse the shared Extension activation guard and preserve all existing Runtime
   authentication, Extension, and Schedule behavior.
8. Add focused unit, API, security, real-PostgreSQL, and OpenAPI coverage; run the
   standard quality gates and a real China-account walkthrough.
9. Update living Runtime documentation and project guidance after the behavior is
   implemented; bump the Runtime package version to `0.7.1`.

### 3.2 Out of Scope

- Health metric, daily summary, workout, weight, device, or synchronization
  tables and APIs.
- Historical backfill, incremental sync, pagination cursors, health-data
  retention, deletion propagation, or health-domain normalization.
- Mi Health Agent tools, tool cards, Workflows, system or personal Schedules,
  notifications, and unattended background synchronization.
- Persisting Profile data or displaying names, birth dates, icons, account IDs,
  device lists, or real health values.
- Password/SMS authentication, non-`cn` regions, multiple Xiaomi accounts per
  Runtime user, credential-key rotation, or a general secret-management service.
- Dynamic plugins, a generic DI container, a custom scheduler, cross-Extension
  dependencies, Edge deployment, Module Federation, or dedicated Logto RBAC.
- Database migration-framework adoption. New tables are created through the
  existing idempotent `metadata.create_all()` contract.
- Web Client implementation, which is owned by Web Client v0.5.0.

## 4. Implementation Design

### 4.1 Package and composition root

Create the Extension using the established vertical-slice layout:

```text
src/spectres/extensions/mi_health/
├── __init__.py
├── extension.py
├── config.py
├── models.py
├── schemas.py
├── auth.py
├── xiaomi.py
├── service/
│   ├── bindings.py
│   └── sessions.py
└── api.py
```

Pure request construction, signature, parsing, and validation helpers may live
in a framework-independent `core/` module when useful. `api.py` remains a thin
adapter; `xiaomi.py` owns external HTTP transport; services own state selection,
persistence, and rotation.

`register(ctx)` must:

1. Load `MiHealthConfig`.
2. Create one `sessionmaker(bind=ctx.db.db_engine)`.
3. Construct the HTTP client, credential cipher, binding service, and session
   service once, injecting the same instances into the router.
4. Create only `mi_health_*` tables with `MiHealthBase.metadata.create_all()`.
5. Return one router and empty Toolkit, Workflow, and Schedule contributions.

Do not perform Xiaomi requests, start threads, create QR challenges, or execute
renewal during import or registration. Use HTTPX through an injectable async
client/transport and declare it as a direct Runtime dependency rather than
relying on another package's transitive dependency. Reuse the already declared
`cryptography` dependency for authenticated encryption.

### 4.2 Configuration and credential protection

Add an Extension-owned `MiHealthConfig` with `env_prefix="MI_HEALTH_"`:

| Setting | Initial contract |
|---------|------------------|
| `MI_HEALTH_REGION` | Explicit; only `cn` is accepted |
| `MI_HEALTH_CREDENTIAL_KEY` | Base64url-encoded 32-byte key; real values only in untracked local overrides |
| `MI_HEALTH_HTTP_TIMEOUT_SECONDS` | Bounded ordinary account/STS/health request timeout |
| `MI_HEALTH_QR_POLL_TIMEOUT_SECONDS` | Bounded long-poll timeout; initial documented value 120 |

A missing or invalid credential key must not prevent unrelated Runtime startup.
Operations that need to decrypt or persist protected material fail closed with a
safe configuration error. Tests use independent synthetic keys. Update both the
complete development and test sections of `.env.example`; do not edit local
environment files.

Use authenticated encryption with a fresh nonce per stored value and bind the
ciphertext to its owner and field purpose as associated data. The exact envelope
must be versioned so a later design can identify it. Plaintext secrets must not
appear in SQL parameters, logs, exceptions, response models, or test snapshots.
Encryption is not a substitute for owner filtering or database access control.

### 4.3 Persistent state

Add two private tables:

| Table | Ownership and purpose | Required behavior |
|-------|-----------------------|-------------------|
| `mi_health_bindings` | One row per Runtime `user_id` | Store region, stable `deviceId`, required Xiaomi/session identifiers, encrypted `passToken`, `serviceToken`, and `ssecurity`, binding state, and safe lifecycle timestamps |
| `mi_health_qr_attempts` | One active QR attempt per owner | Store a random public attempt id, owner, stable attempt `deviceId`, encrypted `lp`, non-sensitive state, creation/update timestamps, and server timing guidance |

`user_id` is the binding primary key. Every read, update, delete, and attempt
lookup includes the verified owner. Never enumerate bindings for administration
or scheduling. Do not expose Xiaomi `userId` or `cUserId` in status responses.

The binding's `deviceId` remains stable across renewal and reauthentication. A
first-time QR attempt generates the value; a reauthentication of an existing
binding reuses it. A new challenge from the same owner supersedes and deletes the
previous active attempt. Terminal, cancelled, superseded, and expired attempts
must remove encrypted `lp` rather than retaining an audit copy.

Serialize session mutation for one owner so concurrent renewal, verification,
QR completion, and unbinding cannot overwrite a newer credential set with a
stale response. Database ownership checks and transactional compare/lock
semantics must cover this race without process-global user state.

### 4.4 Xiaomi authentication and transport

Implement the migrated authentication contract exactly:

- QR challenge uses `sid=miothealth`, `_json=true`, and one stable `deviceId`.
- Accept only expected HTTPS Xiaomi account, STS, and health hosts. Do not follow
  account or STS redirects automatically.
- Treat `loginUrl`, `qr`, and `lp` as sensitive. Return only the QR presentation
  material needed by the current owner; never return `lp`.
- Poll the server-provided `lp` once with the same `deviceId` and a bounded read
  timeout. Browser cancellation is not proof that upstream work stopped; explicit
  cancellation invalidates and deletes the attempt.
- Require the documented success codes and complete fields. Preserve nonce as
  exact decimal text and parse `Extension-Pragma` fallbacks where required.
- Perform STS with the documented SHA1 client signature and
  `_userIdNeedEncrypt=true`; do not send account cookies to STS.
- Accept `miothealth_serviceToken` with the documented fallback. Health requests
  send only the required health cookies, explicit `region_tag: cn`, and a fresh
  nonce.
- Send `passToken` only to the expected Xiaomi account renewal endpoint, never to
  STS or health hosts.
- A security-confirmation result requires owner action and QR recovery; do not
  bypass it or repeatedly submit challenges.
- HTTP 200, plaintext business `code: 0`, or HTTP 401 alone is not sufficient
  evidence of health success or expiry. Validate the expected status, decrypted
  envelope, business code, and response shape.

Map expected provider, validation, timeout, and security-confirmation failures to
safe typed API errors. Preserve no raw provider body when it could contain
sensitive account or session material.

### 4.5 Owner-scoped HTTP contract

Mount one authenticated router under `/api/v1/extensions/mi-health`. All routes
require a normal verified Runtime user and reject missing or internal-only
identity. They never accept an owner field.

| Method | Path | Success contract | Behavior |
|--------|------|------------------|----------|
| GET | `/status` | `BindingStatusResponse` | Read only local state; no Xiaomi request |
| POST | `/auth/qr-challenges` | `QRChallengeResponse` | Create one challenge and supersede the owner's previous active attempt |
| POST | `/auth/qr-challenges/{challenge_id}/poll` | `QRChallengePollResponse` | Poll one owner-matched active attempt once; complete binding after approval and STS |
| DELETE | `/auth/qr-challenges/{challenge_id}` | 204 | Cancel and delete one owner-matched attempt and its sensitive polling material |
| DELETE | `/binding` | 204 | Explicitly delete the current owner's binding and active QR attempts |
| POST | `/session/renew` | `BindingStatusResponse` | Proactively renew with `passToken`, perform STS, and atomically rotate the current owner's session |
| POST | `/session/verify` | `BindingStatusResponse` | Perform one Profile connectivity check, with bounded automatic renewal and one fresh-nonce retry when applicable |

Define request/response models and OpenAPI response schemas for every route.
`BindingStatusResponse` exposes only:

- `status`: `unbound | authenticated | reauth_required`;
- `region`: the explicit supported region;
- nullable `bound_at`, `last_verified_at`, and `last_renewed_at` timestamps.

It must not contain account identifiers, tokens, secrets, `deviceId`, QR data, or
provider response bodies. `QRChallengeResponse` contains a random `challenge_id`,
the sensitive QR presentation payload, `created_at`, and optional server timing
guidance. It does not assert a measured natural expiry. Poll responses use a
typed state such as `waiting | authenticated | owner_action_required | failed`
plus a safe optional failure code; authenticated responses then agree with
`GET /status`.

Use safe machine-readable error codes for at least `not_bound`,
`binding_exists`, `challenge_not_found`, `challenge_expired`,
`owner_action_required`, `authentication_required`, `provider_unavailable`, and
`credential_protection_unavailable`. Use 404 for another user's or unknown
challenge so ownership is not disclosed. Keep existing 401 and Extension-disabled
403 behavior. Validation and provider errors must not leak sensitive URLs or
values through `detail` or logs.

`DELETE /binding` is an explicit owner-requested REST operation, not an Agent
operation; the Web Client supplies a confirmation step. No shared Agent HITL path
is needed because this milestone exposes no Mi Health tools.

### 4.6 Session verification and renewal

`POST /session/verify` first uses the current service session to call Profile.
Consume no personal response fields beyond validating the expected result shape.
On success, update only `last_verified_at` and return the safe binding status.

If a correctly constructed and signed request receives HTTP 401:

1. Attempt `passToken` renewal once.
2. Perform STS and validate all replacement fields.
3. Commit `serviceToken`, `ssecurity`, and any rotated `passToken` atomically.
4. Retry Profile once with a fresh health nonce.
5. If renewal or STS fails, keep the old session; if long-term credentials are
   refused or security interaction is required, mark `reauth_required` without
   deleting the last binding state.
6. Treat a second 401 as failure, not another renewal loop.

`POST /session/renew` exercises the same renewal and STS service without the
initial Profile call. It updates `last_renewed_at` only after successful atomic
rotation. It does not implicitly create a binding, enumerate users, or schedule
future work.

## 5. Security and Isolation Requirements

- Add two-user tests for every route and service read/write. User A must never
  observe, poll, cancel, renew, verify, replace, or delete User B's state.
- Administrator authentication remains self-scoped on these routes; internal
  scheduler identity is not accepted.
- Disabling `mi_health` must return the shared `extension_disabled` response
  before any provider request or database business mutation. Re-enablement works
  without Runtime restart and preserves binding data.
- Audit successful bind, rebind, unbind, renewal, and verification events with
  Runtime `user_id`, event name, result, and trace correlation only. Do not log
  Xiaomi identifiers, tokens, secrets, QR/lp/login URLs, headers, cookies, or
  Profile values.
- Tests must inspect logs, API responses, and representative exceptions for
  synthetic secret sentinels and prove redaction.
- Real credentials and health responses are used only in the owner-approved live
  walkthrough; none are copied into fixtures, logs, documentation, or commits.

## 6. Success Criteria

- [ ] Runtime statically discovers `mi_health`, creates only its two prefixed
  tables, and registers one typed router with no Toolkit, Workflow, Schedule, or
  startup network side effect.
- [ ] Only explicit `cn` configuration is accepted; missing credential protection
  fails closed for dependent operations without blocking unrelated Runtime
  functions.
- [ ] A user can create and present a QR challenge, complete one owner-approved
  poll and STS exchange, and obtain an authenticated binding with a stable
  `deviceId`.
- [ ] QR cancellation, supersession, timeout/expiry, malformed responses, owner
  action, and provider failure clean up or retain state exactly as specified;
  `lp` never survives a terminal attempt.
- [ ] Credentials and transient polling URLs are encrypted at rest, and no
  sensitive material appears in status responses, errors, logs, fixtures, or
  OpenAPI schemas.
- [ ] Proactive renewal and 401-triggered renewal perform STS and atomically
  rotate session material. Failed renewal/STS preserves the old session, and a
  second 401 causes no further renewal.
- [ ] Profile verification succeeds without persisting or returning personal
  Profile fields; explicit unbinding deletes only the current owner's binding
  and attempts.
- [ ] Two-user isolation, administrator self-scope, missing identity rejection,
  and Extension disable/re-enable guards hold for every route.
- [ ] All routes declare accurate response models and safe error contracts;
  existing ETF Grid, authentication, and native Schedule behavior remains
  unchanged.
- [ ] Standard quality checks and real-PostgreSQL tests pass, and the real
  China-account QR/Profile/proactive-renewal walkthrough is approved without
  retaining real sensitive data.

## 8. Verification Plan

### 8.1 Focused automated coverage

Add focused tests following existing Runtime naming and fixture conventions:

```bash
uv run pytest tests/test_mi_health_api.py tests/test_mi_health_auth.py tests/test_mi_health_db.py tests/test_extension_activation.py
uv run pytest tests/test_extensions_loader.py tests/test_main.py tests/test_user_isolation.py
uv run pytest -m db
```

Coverage must include:

- QR challenge, approval, waiting, cancellation, supersession, malformed result,
  security confirmation, and bounded timeout using only synthetic fixtures.
- STS cookie variants, nonce/signature handling, renewal success/refusal, atomic
  rotation, concurrent mutation, and second-401 termination.
- Profile success and invalid-signature/business-code traps without personal-data
  persistence.
- Two-user ownership for every operation, unknown/challenge cross-user 404,
  administrator self-scope, and missing/internal identity rejection.
- Extension-disabled requests causing zero provider calls and zero business
  writes, then re-enablement without restart.
- Ciphertext at rest and log/error/response scans for synthetic tokens, account
  ids, QR payloads, and `lp` values.

uv run ruff check src tests scripts

uv run mypy src tests scripts

Do not add real-Xiaomi calls to the default or real-PostgreSQL suites. Keep live

### 8.3 Live walkthrough

1. Configure a real credential-encryption key and explicit `cn` region only in
   untracked local overrides. Start Runtime with real Logto and PostgreSQL.
2. As ordinary User A, confirm initial status is `unbound`; create a QR challenge
   and complete owner-approved login through Web Client v0.5.0.
3. Confirm status becomes `authenticated`, the binding has the same stable
   `deviceId` after later operations, and the database contains no plaintext
   credential or retained completed-attempt `lp`.
4. Run Profile verification and confirm success without any Profile values in
   API responses or Runtime logs.
5. Run proactive renewal once. Confirm new session material works and is stored
   atomically; do not force natural credential revocation or repeatedly trigger
   account security challenges.
6. Cancel and supersede QR attempts, and exercise provider failure with controlled
   doubles rather than destructive live-account manipulation.
7. As ordinary User B, confirm an independent `unbound` state and no visibility or
   control over User A's binding or challenge. Repeat with an administrator and
   confirm self-scope.
8. Disable Mi Health as an administrator; confirm all seven routes stop before
   business work. Re-enable without restart and confirm the binding remains.
9. Explicitly unbind User A through the confirmed Client action and confirm only
   User A's Mi Health binding and active attempts are removed.
10. Verify existing ETF Grid, chat, Logto login, Extension management, and native
    Schedules remain functional. Stop temporary servers and remove local capture
    or debug artifacts without resetting either database.
