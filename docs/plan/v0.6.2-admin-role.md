## 1. Background

v0.6.0 authenticates every user through Logto and v0.6.1 isolates framework
data by JWT `sub`. Authorization is still flat: the custom
`AnyAuthenticatedProvider` grants every authenticated caller every route,
bypassing Agno's scope checks.

Agno's official self-hosted guidance points to an IdP-owned RBAC model:
[self-hosted deployments define roles in their identity provider or backend
and include the appropriate scopes in the JWT](https://docs.agno.com/agent-os/security/authorization/roles).
AgentOS then verifies the token and enforces those scopes; it does not need a
second role-assignment store.

The design for this milestone follows that guidance:

- **Logto owns** users, `user` / `admin` roles, role assignments, and the API
  resource permissions bundled into those roles.
- **JWT carries** the subject and an array of Agno-native permission strings.
- **AgentOS owns enforcement** through its built-in scope provider and route
  mappings. `agent_os:admin` grants full framework access and bypasses user
  isolation through Agno's existing helpers.
- **Extensions stay out of scope** — no extension scopes, role checks,
  ownership columns, or extension data-isolation changes.

The product experience is deliberately split: `user` gets the AI assistant,
while `admin` gets a management-only console. That presentation work is
owned by the Web Client milestone `v0.3.1-admin-console.md`; it is not a
Runtime deliverable or acceptance dependency. Runtime keeps Agno's full
`agent_os:admin` backend contract, including API and cross-user break-glass.

The important token-format constraint is that Agno expects `scopes` as an
**array of strings**. Logto/OAuth's standard space-delimited `scope` string
is not split by Agno and cannot simply be renamed through `scopes_claim`.
Logto's custom access-token claims will provide the compatible array.

## 2. Current State

- Logto issues ES384 JWTs for the Runtime API resource; Runtime validates
  signature, issuer, and audience and uses `sub` as `user_id`.
- Runtime now uses Agno's default `ScopeAuthorizationProvider`; the custom
  `AnyAuthenticatedProvider` and `src/spectres/auth.py` have been removed.
- UserDirectory JIT provisioning, the disabled-user kill-switch, and
  `user_isolation=True` are live. `tests/test_authorization.py` covers the
  user/admin matrix and `/users`; existing auth/isolation fixtures carry
  explicit scopes.
- Logto is configured with 19 API scopes, default `user` and separate
  `admin` roles, and role-derived `scopes: string[]` custom claims. Real
  tokens were verified for both roles: ordinary user `/agents` → 200 and
  `/users` → 403, admin `/users` → 200, plus ordinary AG-UI and admin
  cross-user session reads.
- An `agent_os:admin` dev token already provides cross-user break-glass, so
  no new isolation middleware is needed.
- Scheduler uses its internal service token. ETF Grid routes require
  authentication but REST/tool data remains shared by explicit contract.

## 3. Scope

### 3.1 In Scope

1. **Logto RBAC configuration**
   - Reuse the existing Runtime API resource
     (`https://spectres.runtime/api`); define permissions using Agno's native
     scope names.
   - Create a global `admin` role containing `agent_os:admin` and assign it
     only to the intended administrator(s).
   - Create a global `user` role, enable it as the default role for new
     users, and assign it to existing ordinary users.
   - Initial `user` scopes, limited to current product functionality:
     - `config:read`, `registry:read`;
     - `agents:read`, `agents:*:run` (the wildcard/global run grant is
       required by AG-UI);
     - `sessions:read/write/delete`, `memories:read/write/delete`;
     - `schedules:read/write/delete`, `approvals:read/write/delete`;
     - `metrics:read`, `traces:read`.
   - Do not add scopes for unused teams/workflows/knowledge/evals or for
     administrative writes in this milestone. Admin inherits all framework
     permissions through `agent_os:admin`.

2. **JWT scope contract**
   - Use Logto `getCustomJwtClaims` to emit the permissions granted for the
     Runtime API resource as a `scopes: string[]` claim. Derive them from
     Logto's server-side authorization context, never from client-supplied
     role or permission claims.
   - Keep the existing `sub`, `iss`, `aud`, `exp`, and ES384 verification
     contract unchanged. Agno's default `scopes_claim="scopes"` then works
     without custom JWT middleware.
   - Verify real Logto tokens for both roles: the claim is an array, admin
     contains `agent_os:admin`, and ordinary users do not contain it.
   - Publish the verified claim shape and example (without real tokens) for
     the Web Client plan. Any token-request or presentation changes are
     owned there, not in this Runtime milestone.
   - Document that role/permission changes apply to newly issued tokens;
     verify behavior after the SDK refreshes the access token. The Runtime
     directory's disabled-user kill-switch remains the immediate revocation
     path.

3. **Runtime scope enforcement**
   - Remove `AnyAuthenticatedProvider` and its wiring. Use Agno's built-in
     `ScopeAuthorizationProvider` (the default verify-only `Authorization`
     behavior) without a custom provider or role store.
   - Keep `user_directory=settings.jwt_auth_enabled` and
     `user_isolation=True` unchanged.
   - Do not add `ADMIN_USER_ID`, `seed()`, managed roles, `roles_claim`,
     `trust_token_scopes`, `/authz`, or role-to-isolation middleware.
   - `/users` remains Agno's directory administration API and becomes
     admin-only through the authoritative `agent_os:admin` scope. Roles
     themselves are administered in Logto, not Runtime.

4. **Verification**
   - Authorization matrix: `user` can read/run the agent and manage its own
     sessions/memories/schedules/approvals; admin-only configuration,
     component, service-account, metrics-write, and `/users` operations
     return 403 for `user` and succeed for `admin`.
   - AG-UI: the `user` scope set passes the route's run check; cross-user
     `thread_id` writes remain refused.
   - Isolation: ordinary A/B tests stay green; admin reads across users via
     the existing scope-based break-glass.
   - Governance: admin can list/update/disable directory users through
     `/users`; ordinary users receive 403. Disabling still denies a valid
     token immediately.
   - Regression: no/invalid token → 401, admin-scope dev tokens and the
     Scheduler internal token keep working, and v0.6.0/v0.6.1 suites stay
     green with fixtures updated to carry explicit user scopes.
   - Extension contract: both roles call the same authenticated ETF Grid
     route and see the same shared data; no extension scope is introduced.
   - Real-IdP API walkthrough: ordinary AG-UI calls and admin `/users` plus
     cross-user read pass with real Logto tokens, including a role change
     followed by token refresh.

5. **Docs sync**
   - Add an ADR selecting Logto-owned RBAC with Agno-native JWT scopes over
     a second Runtime role store.
   - Update authentication architecture with the Logto role/permission
     setup, custom-claims procedure, token example, refresh semantics, and
     admin recovery through Logto.
   - Update data-isolation architecture: admin authority comes from the
     Logto-issued `agent_os:admin` scope, not a managed Runtime role.
   - Link the separate Web Client `v0.3.1-admin-console.md` plan for the
     management-only presentation; do not duplicate its tasks here.
   - Update plan status and `AGENTS.md` confirmed decisions if the previous
     all-users-equal wording needs clarification.

### 3.2 Out of Scope

- **Extension authorization and isolation** — no extension-specific scopes,
  role checks, `user_id` columns, or per-user ETF Grid behavior.
- Agno managed roles, Runtime role assignment, `/authz`, or duplicating
  Logto roles into the Runtime database.
- **All Web Client implementation and UI acceptance** — owned by the
  separate `v0.3.1-admin-console.md` plan in `../Spectres-Web-Client`.
- Backend denial of admin's Agno superuser/break-glass API capabilities;
  management-only behavior is a client presentation concern.
- Organization roles/multi-tenancy, FGA/ReBAC, PostgreSQL RLS, or per-user
  schemas.
- New service-account/PAT functionality; only compatibility with existing
  credentials is regression-tested.
- Scopes for features not currently used, and existing-data migration.

## 4. Success Criteria

- [x] Logto contains `user` and `admin` roles with the documented scope
  matrix; ordinary users receive `user`, and only intended administrators
  receive `admin`.
- [x] Real Logto JWTs contain a valid `scopes` array; admin tokens include
  `agent_os:admin` and user tokens do not.
- [x] `AnyAuthenticatedProvider` is removed; normal product routes work for
  `user`, while admin-only framework and `/users` operations return 403.
- [x] Admin can manage the directory through `/users` and read across users;
  ordinary A/B isolation and cross-user AG-UI rejection remain intact.
- [x] Role/permission changes take effect after token refresh; disabled-user
  denial remains immediate, and Scheduler/admin dev-token regressions pass.
- [x] ETF Grid behavior is unchanged for both roles and no extension scope
  or ownership field is introduced.
- [ ] Runtime quality checks (`ruff`, `mypy`, `pytest`) pass locally and on
  CI; Web Client work is accepted separately.

Local `ruff`, formatting, `mypy`, and the default pytest suite passed on
2026-10-29 (207 passed, 42 deselected). A real Logto role assignment and
revocation was also verified through re-login. CI remains the only open
