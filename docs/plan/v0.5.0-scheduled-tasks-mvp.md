# v0.5.0 — Scheduled Tasks MVP (Agno Scheduler + ETF Grid Daily Sync)

| Field | Value |
|-------|-------|
| **Status** | Review (implementation complete; pending user approval) |
| **Created** | 2026-10-14 |
| **Goal** | Runtime gains a scheduled-task substrate on Agno's built-in AgentOS scheduler: extensions declaratively register cron schedules, and ETF Grid's daily sync + signal computation runs automatically every weekday after market close — deterministic only, zero LLM on the execution path. |

---

## 1. Background

ADR 0007 (Accepted 2026-10-14) settled the scheduler choice and the MVP
scope; [docs/architecture/scheduled-tasks.md](../architecture/scheduled-tasks.md)
holds the design detail. Summary of what is decided:

- **Scheduler**: Agno built-in AgentOS scheduler (in-process poller over
  `agno_schedules` / `agno_schedule_runs`, DB-backed lease, per-schedule
  retries/timeouts). No custom scheduler, no new dependency — verified
  against the pinned agno 3.1.2 (`agno/scheduler/{manager,poller,executor}.py`).
- **MVP carrier**: a schedule is `{cron, endpoint, method, payload}`; the
  executor fires one HTTP call, and for non-run endpoints **2xx = success**.
  Deterministic tasks therefore point straight at extension REST routes.
- **ETF Grid first consumer**: one schedule `etf_grid_daily_sync`
  (`45 15 * * 1-5`, Asia/Shanghai) → a **new composite route**
  `POST /api/v1/extensions/etf-grid/refresh` (sync → compute). Error
  contract: 5xx when all data sources fail or compute fails; 200 +
  per-source `errors` for partial failures.
- **Extension contract**: `ExtensionContribution` gains a `schedules`
  slot (`ScheduleSpec` dataclass); core registers specs via
  `ScheduleManager(...).create(if_exists="update")` at startup.
- **Committed but not built here**: Workflow carriers, Automation Agent,
  notification channel, `SchedulerTools` (ADR 0007 decision 4).

Known unknowns the implementation must measure (ADR 0007 consequences):
misfire/catch-up behavior after downtime, and timezone correctness.

## 2. Current State

- No scheduler code or config anywhere in `src/` (verified: zero hits for
  scheduler/cron in project sources; agno 3.1.2 ships
  `agno.scheduler.ScheduleManager`, `agno.tools.scheduler.SchedulerTools`,
  and the AgentOS `scheduler=True` wiring).
- `src/spectres/main.py` — `create_agent_os()`: db setup →
  `load_extensions(settings, db)` → Team Leader → `AgentOS(...)` →
  routers mounted on `agent_os.get_app()`. Schedule registration slots in
  right after `load_extensions()`; `scheduler=True` goes into the AgentOS
  constructor.
- `src/spectres/extensions/base.py` — `ExtensionContribution` today has
  `toolkits` and `routers` only.
- `src/spectres/extensions/etf_grid/`:
  - `service.py:565` `compute_daily_signals(...)` and
    `marketdata.py` `sync_market_data(...)` — both idempotent (upsert),
    sync, injectable; already composed by `toolkit.py:112`
    `refresh_grid_data()`.
  - `api.py:102` `POST /sync` (network pull; per-source failures reported
    in body `errors`, HTTP 200 — **not schedule-safe on its own**) and
    `api.py:89` `POST /signals/compute` (local recompute).
- `agno_schedules` / `agno_schedule_runs` tables exist in the Agno schema
  inventory (database-schema.md §1, currently "Unused").
- Loader convention (runtime-extensions.md §5.2): an extension whose
  `register()` raises aborts startup with a clear message — schedule
  registration follows the same rule.

## 3. Scope

### 3.1 In Scope

1. **Scheduler enablement** (`spectres/config.py`, `spectres/main.py`)
   - Core settings: `scheduler_enabled` (default true),
     `scheduler_poll_interval` (default 15s), `scheduler_base_url`
     (default `http://127.0.0.1:7777`, must match the serve port).
   - `AgentOS(..., scheduler=settings.scheduler_enabled, ...)` wiring.

2. **Extension contract: `schedules` slot** (`extensions/base.py`,
   `extensions/loader.py` or `main.py`)
   - `ScheduleSpec` dataclass mirroring `ScheduleManager.create`:
     `name, cron, endpoint, method="POST", payload, timezone,
     timeout_seconds, max_retries, retry_delay_seconds, if_exists="update"`.
   - After `load_extensions()`, core iterates all contributed specs and
     registers them via `ScheduleManager(db)`; a failed registration
     aborts startup naming the extension and schedule (loader convention).

3. **ETF Grid composite route** (`etf_grid/api.py`, `etf_grid/service.py`
   if an orchestration helper is wanted)
   - `POST /api/v1/extensions/etf-grid/refresh`: runs
     `sync_market_data()` then `compute_daily_signals()`, returns both
     results in one body.
   - Error contract: 5xx when **all** data sources fail; 5xx when compute
     raises; 200 with per-source `errors` on partial failure.
   - Structured logging per v0.4.2 conventions (INFO summary per refresh;
     ERROR with `exc_info` on failures).

4. **ETF Grid schedule registration** (`etf_grid/extension.py`)
   - Contributes `ScheduleSpec(name="etf_grid_daily_sync",
     cron="45 15 * * 1-5", timezone="Asia/Shanghai",
     endpoint="/api/v1/extensions/etf-grid/refresh",
     max_retries=2, retry_delay_seconds=300)`.

5. **POC validation & documentation of framework behavior**
   - Verify and record in `architecture/scheduled-tasks.md`: misfire /
    catch-up semantics after downtime (fire once? skip?), timezone
     correctness of `next_run_at`, the exact `agno_schedule_runs` record
     shape for simple-request executions.
   - Use `POST /schedules/{id}/trigger` (or `ScheduleManager.trigger`) to
     fire on demand instead of waiting for 15:45.

6. **Tests and quality**
   - Unit: `ScheduleSpec` → `ScheduleManager.create` mapping (mocked
     manager); registration failure aborts with a naming message.
   - Unit: `/refresh` error contract — all-sources-failed → 5xx; partial →
     200 + `errors`; compute failure → 5xx; happy path → 200 with both
     result sections.
   - Integration (dev DB, no LLM): boot app → schedule row exists;
     trigger → `agno_schedule_runs` row with `success`; refresh effects
     visible in `etf_grid_candles` / `etf_grid_signals`.
   - `ruff check`, `ruff format --check`, `mypy`, `pytest` all pass.

7. **Docs sync**
   - `architecture/scheduled-tasks.md`: status → implemented; POC
     findings recorded (misfire etc.).
   - `architecture/runtime-extensions.md`: document the `schedules` slot
     in §4/§6.
   - `architecture/database-schema.md`: `agno_schedules` /
     `agno_schedule_runs` → "In use".

### 3.2 Out of Scope

- Workflow carriers, Automation Agent, anything LLM on the scheduled path
  (ADR 0007 decision 4 — committed evolution, later milestone).
- Notification channel / push service / Client UI for results (open per
  ADR 0007 decision 5).
- `SchedulerTools` on the Team Leader (Master manages schedules) — Phase 2.
- A `ScheduledTaskToolkit` for the Master to read schedule runs — Phase 1
  of Master interaction, later milestone; for now results are read via
  REST / DB / existing etf_grid tools.
- HITL wiring for schedule management; multi-replica scheduler pinning;
  Alembic migrations (project has none yet).
- Trading-calendar awareness (the cron fires on weekday holidays too;
  sync is idempotent and simply finds no new candles — acceptable for MVP).

## 4. Success Criteria

- [x] App boots with the scheduler enabled; `etf_grid_daily_sync` appears
  in `GET /schedules` with cron `45 15 * * 1-5` and timezone
  `Asia/Shanghai`.
- [x] Restarting the app neither duplicates nor resets the schedule
  (`if_exists="update"` idempotency).
- [x] Triggering the schedule on demand produces a `success` row in
  `agno_schedule_runs`, and new rows appear in `etf_grid_candles` /
  `etf_grid_signals` (against the dev DB).
- [x] `/refresh` honors the error contract: simulated total source failure
  → 5xx and a `failed` schedule run (with retries per `max_retries`);
  partial failure → 200 + `errors` and a `success` schedule run.
- [x] Misfire/catch-up behavior is measured and written into
  `architecture/scheduled-tasks.md` (§7 open question resolved).
- [ ] Quality checks pass locally and on GitHub Actions.
