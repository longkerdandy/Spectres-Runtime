## 1. Background

ADR 0013 reclassifies Mi Health as a trusted built-in Runtime and Web Client
Extension. It uses the existing Runtime API token and authenticated-user
authorization model, with no dedicated Mi Health API resource, permission, or
role. The independent Edge implementation is no longer the target topology.

The read-only inventory confirmed:

- Runtime has no executable Mi Health or Mi Health Edge configuration; references
  were limited to ADRs, architecture documents, research, and project guidance.
- Web Client has no Mi Health remote, Module Federation implementation, or Edge
  token/configuration code.
- `Spectres-Edge-Mi-Health` contains three research documents, synthetic
  authentication fixtures, and an independent FastAPI/JWT/Alembic walking
  skeleton. It has no production account binding, credential persistence,
  health-domain tables, or synchronization implementation.
- Logto contains the dedicated `https://spectres.edge.mi-health/api` resource,
  its `mi_health:read` scope, and a `mi_health_reader` role assigned to one user
  and no application. The custom access-token JWT script explicitly lists the
  Edge audience alongside the Runtime audience. No separate Edge OIDC application
  exists.

This milestone prepares a clean development baseline. It does not implement the
built-in Mi Health Extension itself.

## 2. Confirmed Decisions

1. **Research is migrated; the service skeleton is not.** Review reusable
   protocol evidence and synthetic fixtures, but do not port the independent
   FastAPI application, separate JWT verifier, CORS setup, or empty Alembic
   baseline into Runtime by default.
2. **Inventory precedes deletion.** Confirm every Logto resource, permission,
   role, claim, application assignment, and code reference before removing it.
3. **Runtime authentication remains intact.** Cleanup must preserve the Runtime
   API resource, OIDC application, users, user/admin roles, Agno scopes, custom
   JWT behavior needed by Runtime, and existing token verification.
4. **Historical decisions remain historical.** Keep ADR 0012's original decision
   text and amendment notice; update living documents to describe Mi Health as a
   built-in Extension target.
5. **No generic Edge platform removal.** Remove only obsolete Mi Health-specific
   artifacts. ADR 0012 remains valid for future services that genuinely require
   independent Edge deployment.
6. **Destructive and Git operations require owner approval.** Do not delete a
   repository, reset a database, or run Git mutations without explicit approval
   at execution time.

## 3. Scope

### 3.1 In Scope

1. Inventory the old Edge repository and record which documents, fixtures, or
   code fragments should be migrated, retained as history, or discarded.
2. Migrate approved research material into Runtime without secrets, proprietary
   artifacts, raw captures, or personal health data.
3. Inventory and remove obsolete Mi Health Edge settings from Logto, Runtime,
   Web Client, and local deployment configuration where present.
4. Update affected living documentation and mark the old Edge repository as
   superseded after reusable material is preserved.
5. Verify existing Runtime authentication and Web Client behavior after cleanup,
   then run each owning project's standard quality checks.

### 3.2 Out of Scope

- Implementing `src/spectres/extensions/mi_health/` or
  `src/extensions/mi-health/` beyond files needed to hold reviewed fixtures for
  executable tests.
- Real Xiaomi account binding, credential storage, health synchronization,
  health-data tables, Toolkits, Workflows, Schedules, or user-facing pages.
- Adding Mi Health-specific Logto scopes or roles.
- Removing generic built-in Extension enablement or the future independent Edge
  architecture.
- Module Federation implementation or a generic remote catalog.
- Parallel development environments, Git worktrees, separate clones, and related
  dependency, database, or port isolation; ADR 0013 defers these for later study.
- Migrating `research-local/`, original APKs, decompiled trees, raw captures,
  credentials, access tokens, sensitive URLs, or real health records.
- Deleting the old repository or any shared database without a separate explicit
  owner decision.

## 4. Transition Design

### 4.1 Confirm and migrate reusable material

Every tracked source, test, fixture, and document in
`Spectres-Edge-Mi-Health` was inventoried. The final disposition is:

| Old repository material | Final disposition | Target or rationale |
|---|---|---|
| `docs/research/mi-fitness-authentication-contract.md` | Migrated | Runtime `docs/research/mi-health/`; preserved QR login, bounded renewal, atomic rotation, and validation limits |
| `docs/research/mi-fitness-cloud-api.md` | Migrated | Runtime `docs/research/mi-health/`; preserved source versions, evidence, uncertainties, and unsupported-device limits |
| `docs/research/environment.md` | Migrated selectively | Retained reusable research setup and artifact handling; omitted obsolete independent-service checks |
| Synthetic authentication fixtures | Reviewed; not migrated | Manifest confirms all values are synthetic; copy individual fixtures only when future Mi Health tests consume them |
| FastAPI app, JWT auth, CORS, config, logging, tests, and empty Alembic baseline | Retained only as history | No production domain behavior exists to migrate; future behavior will use Runtime Extension contracts |
| Old README, architecture, AGENTS, milestone plans, and development configuration | Retained only as history | Not current design; README and AGENTS now carry a superseded notice |
| `research-local/` and other sensitive artifacts | Not accessed or migrated | Left untouched and excluded from commits and documentation |

For each migrated document:

- Preserve evidence dates, source versions, known limitations, and the distinction
  between validated research and production behavior.
- Update topology-specific language to the built-in Extension model without
  rewriting historical protocol evidence.
- Update inbound links, including ADR 0013's authentication-research reference.
- Do not include credentials, tokens, QR payloads, sensitive login URLs, account
  identifiers, or real health data.

### 4.2 Clean obsolete Logto and code settings

#### Logto inventory and cleanup

Inventory through Logto Console or supported management APIs rather than ad-hoc
SQL. Record the resource identifiers and dependency graph before mutation:

- The dedicated Mi Health Edge API resource and its audience.
- `mi_health:read` and any other Edge-only permissions.
- `mi_health_reader` or any other Edge-only role and its assignments.
- Custom JWT claims or scripts that add Edge-only permissions.
- OIDC application resource/role assignments used only by the old Edge flow.
- Any deployed callback, CORS, or environment setting that refers to the Edge
  audience or service.

Take a restorable configuration export or database backup before destructive
changes. Remove only confirmed Mi Health Edge-only artifacts after the owner
approves the inventory. Preserve the Runtime API resource, Runtime permissions,
OIDC application, users, existing user/admin role assignments, and Runtime JWT
claims. Do not reset the Logto database.

After cleanup, verify that:

- Runtime authorization-code flow with PKCE still issues usable Runtime tokens.
- Ordinary-user and administrator tokens retain their existing Runtime scopes.
- Runtime APIs and Extension catalog/activation operations behave as before.
- No active client or service still requests the removed Edge audience.

#### Code and deployment cleanup

Search Runtime, Web Client, deployment files, examples, and developer guidance
for Mi Health Edge-specific references. Remove only confirmed obsolete settings,
clients, token acquisition, CORS entries, remote metadata, and service startup
configuration. If the confirmed inventory contains no code or configuration to
remove, record that result rather than creating unrelated edits.

The preliminary inventory found no such executable Runtime or Web Client
configuration, so Logto and documentation are expected to be the main cleanup
surfaces.

If tracked Runtime environment examples change, update both complete development
and test sets in `.env.example`. The owner manages `.env`, `.env.test`, and local
override files; do not edit them directly. Do not remove shared settings merely
because the old Edge also used them.

After research is preserved and the owner approves retirement, mark
`Spectres-Edge-Mi-Health` as superseded in its README and AGENTS guidance.
Repository archival or deletion is a separate operation, not a prerequisite for
starting built-in Extension development.

### 4.3 Update living documentation

Update only documents whose current or target behavior changes:

- Runtime `AGENTS.md`: identify Mi Health as a built-in Extension target and
  replace the old Edge repository reference with migrated research where useful.
- `docs/architecture/system-architecture.md`: remove Mi Health from the current
  independent-Edge example and list the built-in Mi Health Extension as not yet
  implemented. Keep the generic future Edge model.
- `docs/architecture/runtime-extensions.md`: mention Mi Health only as a planned
  Extension until implementation exists; do not present its routes, tables, or
  schedules as current behavior.
- ADR 0013: update migrated research links and any cleanup assumptions that the
  final inventory disproves.
- Web Client living architecture and guidance: describe Mi Health as a future
  built-in Extension using the Runtime token, without adding a Module Federation
  remote.
- Old Edge README/AGENTS: state that the independent topology was superseded by
  Runtime ADR 0013 and point to migrated research.

Do not rewrite completed milestone plans or ADR 0012's historical body merely to
make old statements match the new topology. Their status and amendment context
already explain the decision history.

## 7. Verification Plan

### Automated checks

Run Runtime checks after code, configuration, or documentation cleanup:

```bash
uv run ruff check src tests scripts
uv run ruff format --check src tests scripts
uv run mypy src tests scripts
uv run pytest
uv run pytest -m db
```

Run Web Client checks when that project changes:

```bash
npm run lint
npm run typecheck
npm run build
```

Use focused documentation-link and repository searches to confirm that no living
document points to retired research paths or describes Mi Health as an active
independent Edge. Historical ADR and completed-plan references may remain when
their amendment context is clear.

### Live walkthrough

1. Record the current Runtime OIDC application, API resource, roles, permissions,
   and custom-claims behavior before cleanup.
2. Back up or export the approved Logto configuration and perform only the
   reviewed Edge-only deletions.
3. Sign in as an ordinary Runtime user and call an existing authenticated API.
4. Sign in as an administrator and verify Extension catalog/state management and
   existing administrator behavior.
5. Start Runtime and Web Client from the integrated baseline and verify existing
   ETF Grid and core navigation behavior.
