## 1. Background

The current Extension mechanism already matches the accepted static-discovery,
global-activation, native-Workflow, and ownership-isolation architecture. No new
plugin platform or execution abstraction is needed. The remaining issues are
local implementation debt in the ETF Grid reference Extension and Runtime
assembly:

- `POST /api/v1/extensions/etf-grid/refresh` is an obsolete administrator/internal
  composite operation. The automatic system Schedule now targets only
  `etf_grid_data_sync`; current-user recomputation is available through REST,
  an agent tool, and `etf_grid_recompute`.
- The `refresh_grid_data` agent tool is also a composite operation: it synchronizes
  shared market data and then recomputes the current run owner's signals. It does
  not enumerate other users, but it does not give the Agent independent sync and
  compute operations.
- ETF Grid API, Toolkit, and Workflow factories each construct their own service
  objects. Services obtain their session factory through a process-global
  database helper instead of the `ExtensionContext` supplied at registration.
- Surviving ETF Grid routes return loosely typed dictionaries without FastAPI
  response models, leaving the public HTTP contract weakly checked.
- `list_grid_trades` reads the owner's complete filtered ledger and slices it in
  Python even though the Ledger service already supports SQL pagination.
- Runtime creates one `ExtensionStateService` for management/Toolkit/Workflow
  guards and another for REST mounting. Both currently read the same database,
  but the duplicate assembly is unnecessary.

The owner has explicitly approved removal of both composite refresh surfaces.
The Agent must instead have separate shared-data sync and current-user signal
compute tools with semantics corresponding to the surviving REST operations.

## 2. Confirmed Decisions

1. **Delete the composite REST endpoint.** Remove
   `POST /api/v1/extensions/etf-grid/refresh`; retain `/sync`,
   `/signals/compute`, trade routes, both Workflows, and all native Schedules.
2. **Replace the composite agent tool.** Remove `refresh_grid_data` and expose
   `sync_grid_data` plus `compute_grid_signals`. The Agent calls domain services
   through the Toolkit rather than making HTTP requests to its own Runtime.
3. **Compute is always current-user only.** `compute_grid_signals` derives its
   owner exclusively from verified `RunContext.user_id`, accepts no ownership
   argument, and never enumerates ledger owners. `sync_grid_data` changes shared
   data only and never recomputes any user's signals.
4. **Do not replace all-user fan-out.** The deleted REST endpoint's enumeration
   and recomputation of every ledger owner has no replacement. Shared sync and
   private recompute remain independent operations with no hidden orchestration
   or ordering guarantee.
5. **Use an Extension-local composition root.** ETF Grid creates its database
   session factory and domain services once per `register()` call from
   `ExtensionContext.db`, then injects the same instances into its three
   adapters. No generic dependency-injection framework is introduced.
6. **Preserve behavior except for the approved refresh-surface changes.** Surviving
   route paths, authorization, JSON field names and values, Decimal/date string
   serialization, unrelated tool names and envelopes, Workflow outputs, and
   Schedule configuration remain compatible.
7. **Type the HTTP boundary without rewriting the domain core.** Add Pydantic
   request/response schemas and route `response_model`s. Pure `core/` remains
   framework-independent; a wholesale conversion of every internal dictionary is
   not required.
8. **Keep activation state database-backed and immediate.** Reuse one state
   service instance during Runtime assembly, but do not add a cache or change
   enable/disable semantics.
9. **Historical documents remain historical.** Update living architecture and
   project guidance; do not rewrite accepted ADRs or completed milestone plans
   that describe old refresh behavior in their historical context.

## 3. Scope

### 3.1 In Scope

1. Remove the composite ETF Grid `/refresh` route and code used only by that
   route.
2. Remove `refresh_grid_data` and add independent `sync_grid_data` and
   `compute_grid_signals` agent tools.
3. Make ETF Grid dependency assembly explicit through `ExtensionContext` and
   constructor/function injection.
4. Reuse one `ExtensionStateService` across core management, Toolkit/Workflow
   guards, and Extension REST mounting.
5. Add typed schemas and response models to every surviving ETF Grid REST route.
6. Push Toolkit trade-list limits into SQL and validate the tool's `limit`
   argument consistently with the REST route.
7. Update focused unit and real-PostgreSQL tests, living documentation, and the
   reference Extension guidance.
8. Run standard quality checks and an API/tool/Workflow activation and ownership
   walkthrough.

### 3.2 Out of Scope

- Removing `POST /sync`, `POST /signals/compute`, either ETF Grid Workflow, or
  any system/personal Schedule.
- Keeping `refresh_grid_data` as an alias, compatibility wrapper, or hidden
  sync-plus-compute operation.
- Recreating all-ledger-owner recomputation in a service, Toolkit, Workflow, or
  Schedule.
- Mi Health implementation or changes to its accepted architecture.
- Dynamic plugins, lifecycle hooks, entry-point discovery, a generic DI container,
  Service Locator, Action registry, custom scheduler, cross-Extension
  dependencies, per-user activation, or Extension-specific Logto scopes.
- Database schema changes, table migrations, Schedule-row migration, dependency
  upgrades, or environment-variable changes.
- A wholesale DTO rewrite of all service/provider internals, activation-state
  caching, or unrelated performance work.
- Web Client implementation. Living Runtime documentation will record the tool
  replacement so any Client tool-name renderer mapping can be handled in its
  owning project.

## 4. Implementation Design

### 4.1 Remove the obsolete composite REST path

In `src/spectres/extensions/etf_grid/api.py`:

- Delete the `@router.post("/refresh")` handler, including shared sync,
  all-source-failure mapping, ledger-owner enumeration, per-user recomputation,
  and aggregate result logging.
- Remove the now-unused `require_admin_or_internal` import and HTTPException
  import if no surviving route needs them.

Remove code that becomes dead solely because of this deletion:

- `require_admin_or_internal()` from `etf_grid/auth.py` after confirming no
  callers remain.
- `EtfGridLedgerService.list_user_ids()` from `etf_grid/service/ledger.py`.
- The `/refresh` test class, fixtures, helpers, and `list_user_ids()` database
  test. Add one focused regression assertion that the removed route returns 404
  and cannot invoke synchronization or recomputation.

Do not alter stored Schedules. The supported system Schedule already targets
`/workflows/etf_grid_data_sync/runs`, and personal recompute Schedules target
`etf_grid_recompute`.

### 4.2 Split agent sync and current-user computation

Replace `refresh_grid_data` in `src/spectres/extensions/etf_grid/toolkit.py`
with these tools:

| Tool | Identity and inputs | Domain operation | Result |
|------|---------------------|------------------|--------|
| `sync_grid_data(run_context)` | Require a verified run owner; accept no user id | Call only `sync_market_data()` for shared candles and valuation | Standard `{ok, data}` envelope containing `candles`, `valuation`, and `errors` |
| `compute_grid_signals(run_context)` | Require verified `RunContext.user_id`; accept no user id | Call only `compute_daily_signals(user_id=RunContext.user_id)` for the configured portfolio | Standard `{ok, data}` envelope containing `signals` and `skipped` |

Implementation requirements:

- Keep network-bound `sync_grid_data` asynchronous and run its blocking provider
  pipeline through `asyncio.to_thread()`, preserving the existing event-loop
  behavior without chaining signal computation in the worker.
- `compute_grid_signals` performs local database/domain work only. It must not
  call `sync_market_data`, fetch provider data, enumerate ledger owners, or accept
  a payload/LLM-supplied owner.
- Both tools use `_run_user_id()` and fail closed when run identity is missing.
  Sync requires an authenticated caller just like `POST /sync`, even though its
  persisted data is shared.
- Sync mirrors `POST /sync`: per-source failures remain in `errors`; a total
  source failure is returned through the normal tool result contract rather than
  triggering private recomputation. Compute mirrors `POST /signals/compute` and
  returns its per-symbol `signals`/`skipped` result.
- Remove `_refresh_grid_data_sync()` and the composite sync-plus-compute result
  merge. Do not leave an alias with the old tool name.
- Register exactly five tools: `get_grid_status`, `sync_grid_data`,
  `compute_grid_signals`, `record_grid_trade`, and `list_grid_trades`.

Update Toolkit tests to verify independent operation, async thread offload for
sync, missing-identity failures, current-owner compute, two-user isolation, and
that neither tool performs the other tool's operation. Extension-disabled tests
must cover both new entry points and prove no provider, database, or signal side
effects occur while disabled.

### 4.3 Build ETF Grid services in `register()`

Use `src/spectres/extensions/etf_grid/extension.py` as the only production
composition root for ETF Grid services:

1. Load `EtfGridConfig`.
2. Create `sessionmaker(bind=ctx.db.db_engine)`.
3. Construct one each of `EtfGridLedgerService`, `EtfGridCandleService`,
   `EtfGridValuationService`, and `EtfGridSignalService` with that factory.
4. Pass the same four instances to `create_router()`, `EtfGridToolkit`, and
   `create_workflows()`.
5. Keep table creation idempotent and limited to registration; do not add network
   calls, threads, or Schedule execution.

Require the session factory in each service's explicit constructor and remove
`etf_grid/db.py` once no imports remain. Do not retain a base class solely to
hold the factory. Remove production fallback construction through
`get_postgres_db()` so Runtime execution cannot silently bypass the injected
context. Pass required services explicitly through orchestration and provider-sync
functions rather than recreating defaults inside the call chain.

Keep configuration loading and test doubles lightweight. Tests may construct
services with an explicit test `sessionmaker` or inject fakes directly; they must
not need the process-global Runtime database helper merely to build an adapter.

Do not move these services into core Runtime and do not create a generic service
registry reusable by all Extensions. Mi Health will own its own composition root
when implemented.

### 4.4 Reuse the Runtime Extension state service

Change Runtime assembly so the `ExtensionStateService` initialized in
`create_agent_os()` is also passed to `mount_extension_routers()`:

- Return the initialized state service alongside AgentOS and loaded Extensions
  from `create_agent_os()`.
- Require that instance in `mount_extension_routers()` instead of constructing a
  second service from `get_postgres_db()`.
- Update the module-level application assembly and affected tests/callers.

This is an internal assembly-signature change, not an HTTP contract change. Keep
`ExtensionStateService.initialize()`, catalog/admin routes, activation guards,
unknown-id behavior, and database reads unchanged. Do not store mutable user or
business state in the application object.

### 4.5 Add typed ETF Grid HTTP schemas

Add `src/spectres/extensions/etf_grid/schemas.py` for FastAPI/Pydantic request
and response contracts. Move `TradeCreate` there and define response models for:

- `GET /status`, including nested latest-signal and order-advice structures;
- `POST /signals/compute`, including per-symbol signals and skipped reasons;
- `POST /sync`, including nullable source results and per-source errors;
- `GET /trades`, including the paginated envelope and trade rows;
- `POST /trades`, using the same persisted-trade representation as the list
  route where the existing payload allows it.

Declare these models as `response_model` on every surviving route. Keep response
serialization compatible with `to_jsonable()`: Decimal values remain strings,
dates/datetimes remain ISO strings, nullable fields retain their current null
semantics, and dynamic symbol/error maps remain keyed as before.

Do not add response envelopes where none exist, rename fields, hide currently
returned ownership/source fields, or change 200/201/401/403/422 behavior. The
only removed HTTP contract is the explicitly approved `/refresh` endpoint.

Add focused schema tests that compare representative responses with the existing
JSON contract and verify the generated OpenAPI operations declare their response
schemas. Existing tool envelopes and Workflow result shapes remain unchanged;
the new tools reuse the corresponding REST result data inside `{ok, data}`.

### 4.6 Push Toolkit pagination into SQL

Update `EtfGridToolkit.list_grid_trades()` in `etf_grid/toolkit.py` to:

- Validate `limit` as an integer from 1 through 200 before calling the Ledger
  service; invalid values return the existing structured tool-error envelope and
  perform no query.
- Call `list_trades(..., limit=limit)` with the existing owner and newest-first
  sort specification.
- Remove Python `rows[:limit]` slicing.

Keep the default limit of 20 and the existing success payload shape. Add tests
proving the service receives the limit, only the requested page is returned, and
zero, negative, and greater-than-200 limits fail closed without a Ledger call.
Real-PostgreSQL coverage must confirm that owner filtering still applies before
pagination.

## 5. Success Criteria

- [x] `POST /api/v1/extensions/etf-grid/refresh` no longer exists and returns 404;
  repository searches find no executable caller, all-user fan-out, or dead
  refresh-only helper.
- [x] `refresh_grid_data` and its composite sync-plus-compute path no longer exist.
  The Toolkit exposes exactly `get_grid_status`, `sync_grid_data`,
  `compute_grid_signals`, `record_grid_trade`, and `list_grid_trades`.
- [x] `sync_grid_data` performs shared-data synchronization only.
  `compute_grid_signals` performs no synchronization and derives its exclusive
  target owner from verified `RunContext.user_id`; cross-user input cannot
  redirect either operation.
- [x] `/sync`, `/signals/compute`, trade APIs, both Workflows, and native Schedule
  behavior remain available and unchanged.
- [x] One ETF Grid registration creates one shared session factory and one set of
  services used by REST, Toolkit, and Workflow adapters; runtime paths no longer
  depend on `etf_grid/db.py` or hidden `get_postgres_db()` construction.
- [x] Extension registration remains idempotent and performs no network or
  Schedule execution side effects.
- [x] Core management, Toolkit/Workflow guards, and Extension REST guards use the
  same initialized `ExtensionStateService`; disable/re-enable remains immediate
  without caching or application reconstruction.
- [x] Every surviving ETF Grid REST operation has a typed response contract, and
  representative JSON responses retain their previous field names, values, nulls,
  serialization, and status codes.
- [x] `list_grid_trades` applies its validated limit in SQL rather than reading
  and slicing the complete ledger; private ownership filtering remains intact.
- [x] Living documentation describes five surviving ETF Grid routes, the five
  revised agent tools, and the explicit Extension-local composition pattern;
  historical ADRs and completed plans are not rewritten.
- [x] Standard Runtime quality checks and relevant real-PostgreSQL integration
  tests pass.

