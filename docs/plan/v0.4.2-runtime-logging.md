# v0.4.2 — Runtime Logging & Agent-Diagnosable Errors

| Field | Value |
|-------|-------|
| **Status** | Completed |
| **Created** | 2026-09-30 |
| **Goal** | Runtime gains structured, agent-diagnosable logging: every extension (starting with `etf_grid`) emits JSON logs correlated by `trace_id`, and tool failures return a structured error carrying that `trace_id` plus a concrete hint for investigating via the shell tool the Team Leader already has. |

---

## 1. Background

`src/spectres` currently has **zero logging**: `csindex` retries silently,
`marketdata.sync_market_data` swallows tracebacks into `str(exc)`, tool
invocations and trades leave no audit trail — all in tension with AGENTS.md
§4 ("Use structured logging. Tool invocations, Edge commands, and
permission checks must be auditable.").

The motivating scenario: the Team Leader calls an `etf_grid` tool, the call
fails, and today the agent gets a raw exception with no way to investigate.
After this milestone the agent receives a structured error with a
`trace_id` and a concrete lookup hint, and can retrieve the full log
context of that call — error message, retry attempts, stack summary — via
its existing `ShellTools` (grep/jq over the JSONL file), then explain or
retry accordingly.

Design decisions confirmed during planning:

- **Library**: stdlib `logging` + a small custom JSON formatter. Zero new
  dependencies; every framework in the stack (uvicorn, SQLAlchemy, Agno,
  ftshare SDK) already speaks stdlib logging. `structlog` remains a
  possible later upgrade; the naming and field conventions chosen here
  migrate cleanly.
- **Storage**: one shared JSON Lines file for the whole Runtime
  (`logs/runtime-YYYY-MM-DD.jsonl`, daily rotation + retention), plus
  stdout. A single file keeps a one-command `grep <trace_id>` sufficient
  across the runtime/extension boundary; per-extension filtering works via
  the `extension` field on every record. Per-extension files or a SQLite
  index are deferred evolutions.
- **Agent access**: **no dedicated log-query toolkit**. The Team Leader
  already has `ShellTools` (`spectres/tools/builtin.py`), which can grep
  the JSONL file directly; a purpose-built query toolkit would duplicate
  that capability at extra code cost. The milestone instead invests in
  *discoverability*: structured tool errors carry the `trace_id` and an
  explicit lookup hint, and the Team Leader instructions document the log
  location and record shape. A dedicated read-only log tool is reconsidered
  when (a) `ShellTools` gets restricted for security, or (b) shell-based
  log lookups prove too token-expensive or error-prone in practice.

## 2. Current State

- `etf_grid` extension fully functional (v0.4.0 + v0.4.1): config,
  services, sync pipeline, toolkit (4 functions), API router (6 endpoints).
  No logging anywhere; error handling gaps documented (silent retries in
  `csindex.py:51-52`, traceback loss in `marketdata.py:148-156`, raw
  exceptions from `toolkit.py`).
- `main.py`: `create_agent_os()` loads extensions between db setup and app
  assembly — the natural anchor for one-time logging configuration.
- `spectres/config.py`: pydantic-settings `Settings` — logging settings
  join here.
- `spectres/tools/builtin.py`: Team Leader already carries `ShellTools`
  (plus calculator/website/tavily) — the channel for agent log access.
- `spectres/agents/team_leader.py`: instructions are minimal; they gain a
  short log-lookup note.

## 3. Scope

### 3.1 In Scope

1. **Logging foundation** (`spectres/logging.py`)
   - `configure_logging(settings)`: root handler(s) — stdout plus a daily
     rotated JSONL file under `settings.log_dir` with
     `settings.log_retention_days` retention. `log_format=json|text`
     (text for local dev, json for deployment); `log_level` default INFO.
     Uvicorn access logs route into the same configuration.
   - `JsonFormatter`: emits one JSON object per line with fixed fields —
     `ts`, `level`, `logger`, `extension` (derived from logger name),
     `event`, `message`, `trace_id`, plus arbitrary `extra` fields and
     `exc_info` (exception type, message, top frames — not a full
     200-line dump).
   - **Trace context**: a `contextvars.ContextVar[str | None]` holding the
     current `trace_id`; helpers `new_trace() -> str` (short uuid),
     `current_trace_id()`, `bind_trace(trace_id)`. Every log record
     automatically picks up the active trace id.
   - FastAPI middleware (`spectres/middleware.py` or inside
     `logging.py`): generates/binds a `trace_id` per HTTP request.

2. **Settings** (`spectres/config.py`): `log_level`, `log_format`,
   `log_dir`, `log_retention_days` — all with defaults so existing `.env`
   files keep working. `logs/` added to `.gitignore`.

3. **`etf_grid` instrumentation**
   - `extension.py`: INFO on successful register (symbols, contributions).
   - `marketdata.py`: per-source failure logs ERROR with `exc_info`
     (traceback no longer lost); INFO summary per sync run (rows per
     source, errors).
   - `csindex.py`: WARNING per retry attempt (`attempt=n/5`, elapsed);
     ERROR before the final `RuntimeError`.
   - `service.py`: INFO audit record on `record_trade` success
     (`event=trade_recorded`, symbol/side/quantity/price/net_amount);
     DEBUG for gate skips in `compute_daily_signals`.
   - `api.py`: WARNING on 422 conversions.

4. **Toolkit error contract + agent discoverability**
   (`etf_grid/toolkit.py`, `spectres/agents/team_leader.py`)
   - Each `etf_grid` tool wraps its body in a boundary try/except — on
     failure it binds a new `trace_id` when none is active, logs ERROR
     (with `exc_info`), and returns a structured result instead of
     raising:

     ```json
     {
       "ok": false,
       "error": {
         "type": "ValueError",
         "message": "side must be buy/sell",
         "trace_id": "a1b2c3d4",
         "hint": "Investigate with the shell tool: grep a1b2c3d4 logs/runtime-<today>.jsonl"
       }
     }
     ```

     On success: `{"ok": true, "data": ...}`. Docstrings explain the
     contract so the agent knows `ok: false` means "read the hint".
   - Team Leader instructions gain a short note: extension tools return
     `{"ok", "data"|"error"}`; on failure use the shell tool to grep the
     JSONL log (`logs/runtime-YYYY-MM-DD.jsonl`) by `trace_id`; records
     are one JSON object per line with `ts/level/event/extension/message`
     fields.

5. **Extension conventions** (`docs/architecture/runtime-extensions.md`):
   extensions must use `logging.getLogger(__name__)` only (never
   configure handlers); no silent `except: pass` — failures logged at
   WARNING or above; sensitive operations logged as structured audit
   events; tool errors follow the structured-error + `trace_id` + `hint`
   contract.

6. **Tests and quality**
   - Unit: JSON formatter shape, redaction (no API key / DB url in any
     record), trace contextvar propagation, daily-rotation wiring.
   - Unit (caplog): etf_grid instrumentation points — retry WARNINGs,
     sync ERROR with exc_info, `trade_recorded` audit event.
   - Unit: toolkit error contract — failure returns `ok: False` with a
     `trace_id` that actually appears in the log file, and the `hint`
     references the real file path pattern.
   - End-to-end (as feasible without an LLM): simulated tool failure →
     structured error → grep the JSONL file by `trace_id` finds the
     matching ERROR record (mirrors exactly what the agent will do).
   - `ruff check`, `ruff format --check`, `mypy`, `pytest` all pass.

### 3.2 Out of Scope

- **Dedicated log-query toolkit** (`search_logs`/`get_trace`) — deferred;
  `ShellTools` covers agent log access today. Revisit triggers:
  `ShellTools` restriction, or proven token/error-rate cost of shell
  lookups.
- structlog migration, per-extension log files, SQLite/DB log index,
  external log aggregation (Loki/ELK) — deferred evolutions.
- Log-based alerting/metrics dashboards.
- Shipping logs to the Client layer; the agent is the log consumer.
- `ShellTools` permission hardening (it can currently read arbitrary
  files incl. `.env`) — a pre-existing, separate security topic.
- Audit-grade trade storage in a DB table (logs suffice for MVP; a
  dedicated audit table is a later milestone if retention rules diverge).
- Multi-tenant log isolation/ACL — single-user deployment (ADR 0005).
- Fixing unrelated error-handling inconsistencies found in the same
  review (API 422 uniformity, `GateConfig.metric` Literal, FTShare
  retry/timeout) — separate milestone candidates.

## 4. Success Criteria

- [x] Runtime boots with logging configured; extension load failures are
  logged with extension name and traceback.
- [x] A failing tool call returns `{"ok": false, "error": {..., "trace_id",
  "hint"}}` and grepping the JSONL file by that `trace_id` returns the
  ERROR record explaining the failure (works for at least: invalid
  `record_grid_trade` input, sync with a failing source, missing FTShare
  API key).
- [x] Team Leader instructions document the log file location and record
  shape, so the agent can run the grep without being told the path.
- [x] csindex retries and sync per-source failures appear in logs with
  WARNING/ERROR and full exception info — nothing is silent anymore.
- [x] Every `record_trade` produces a `trade_recorded` audit record.
- [x] No secret (FTShare API key, DB credentials, LLM keys) appears in
  any log record under test.
- [x] Quality checks pass locally and on GitHub Actions.
