## 1. Background

The web client (`../Spectres-Web-Client`) is preparing milestone v0.2.0: a
standalone ETF Grid page that talks directly to this extension's REST API.
Its pre-implementation audit of the current working tree confirmed the six
endpoints exist with the documented semantics, but found two contract gaps
that would force the client to build workarounds:

1. **List endpoints silently truncate.** `GET /trades` and `GET /signals`
   accept `limit` (default 20) but have **no `offset` and no `total`**
   (`api.py` `get_trades` / `get_signals`): rows beyond the limit are
   dropped invisibly. The client's trade ledger is a "full-width,
   filterable" view — silent truncation makes it incorrect by default.
2. **422 responses have two shapes.** Domain rejections raise
   `HTTPException(422, detail=str)` (`api.py` `create_trade`), while
   pydantic body rejections (`price <= 0`, invalid `side`, …) produce
   FastAPI's default `detail=[{loc, msg, type}]`. A client must implement
   two error renderers for the same status code.

Both are cheap to fix **now**: the only consumer (web client v0.2.0) has
not been written yet, so the response-shape change breaks nothing.

Read first: `AGENTS.md`, `docs/architecture/runtime-extensions.md` §7
(the `etf_grid` reference-extension section — its "Client contract" bullet
currently covers the chat side only), `docs/plan/v0.4.1-etf-grid-api-tools.md`
(the milestone that shipped these endpoints).

Prior dependencies: v0.4.1 (endpoints exist), v0.4.2 (logging — the
tool-call envelope landed there and is **not** affected by this milestone),
v0.4.3 (framework upgrade).

Key constraints:

- **Thin adapter**: `api.py` stays free of business logic; pagination math
  over the already-materialized row lists is adapter-level plumbing, not
  domain logic. SQL-level pagination is a later optimization if the tables
  grow (single-user MVP scale does not need it).
- **Toolkit untouched**: the four Agent tools keep their current shapes
  (including the v0.4.2 `{ok, data}/{ok, error}` envelope). This milestone
  changes only the HTTP surface.
- **Breaking shape change is in scope deliberately**: `GET /trades` and
  `GET /signals` switch from a bare list to an envelope. Flagged in the
  commit message.

## 2. Current State

- `etf_grid/api.py`: six endpoints under `/api/v1/extensions/etf-grid`;
  `get_trades` filters `start`/`end` in the adapter and slices
  `rows[:limit]`; `get_signals` slices `rows[:limit]`; both return bare
  lists. `create_trade` maps `ValueError` to `HTTPException(422,
  detail=str)`.
- `etf_grid/service.py`: `list_trades` / `list_signals` return full
  filtered row lists (dicts) — sufficient for adapter-level pagination.
- Tests: `tests/test_etf_grid_api.py` covers the endpoints with FastAPI
  `TestClient`; it will need updates for the new shapes.
- Docs: `runtime-extensions.md` §7 documents the chat-side client
  contract only; the REST envelope/error contract is new content added by
  this milestone.

## 3. Scope

### 3.1 In Scope

1. **Pagination envelope for list endpoints**
   - `GET /trades` and `GET /signals` gain an `offset` query parameter
     (default 0, `ge=0`); `limit` keeps its default of 20 but gains Query
     validation (`ge=1`, `le=200`) — today a negative `limit` silently
     mis-slices (`rows[:-5]`), and tightening it to a 422 is safe because
     the only consumer has not been written yet.
   - Response shape becomes
     `{"items": [...], "total": int, "limit": int, "offset": int}`, where
     `total` is the post-filter row count before slicing.
   - Existing filters (`symbol`, `start`, `end`) are unchanged and apply
     before counting.

2. **Unified 422 error contract**
   - Canonical guarantee: every 422 from this router has `detail` as a
     **list of objects carrying `loc` / `msg` / `type`**. FastAPI's native
     validation items may additionally include `input` and `url` — the
     contract guarantees the three fields only; clients must ignore extra
     keys.
   - `create_trade`'s domain rejection is converted to the guaranteed
     shape (single-element list, `loc: ["body"]`, `type: "value_error"`),
     so every 422 from this router renders through one client code path.
   - The contract is documented in `runtime-extensions.md` §7 — note that
     §7's existing "Client contract" bullet covers only the *chat* side
     (markdown + CopilotKit cards); this milestone **adds** the REST
     contract (envelope + 422 shape) there as new content.

3. **Tests** (`tests/test_etf_grid_api.py`)
   - Pagination: `offset`/`limit` windowing, `total` reflects post-filter
     count, defaults unchanged when params omitted.
   - Validation: `limit=0` / negative `limit` / negative `offset` now
     return 422 (new `Query` constraints).
   - Error contract: a pydantic rejection and a domain rejection both
     return 422 with `detail` as a list of objects carrying
     `loc`/`msg`/`type`.

4. **Docs & versioning**
   - Update `runtime-extensions.md` §7 (envelope shape, 422 contract).
   - Bump `pyproject.toml` `version` from `0.2.1` to `0.4.4`. This is an
     **alignment, not an increment**: the field has been stale since
     v0.2.1 while milestones moved on. Confirmed convention from this
     milestone onward: the project version tracks the milestone number,
     so each milestone plan includes the bump as a task.

### 3.2 Out of Scope

- **SQL-level pagination / cursor-based pagination** — in-memory slicing
  over service-returned rows is sufficient at single-user scale; revisit
  if ledgers grow large.
- **New filters, sorting controls, or additional endpoints** — the client
  milestone works with the existing set.
- **Toolkit / AG-UI surface changes** — chat-side shapes were finalized
  in v0.4.2; nothing here touches them.
- **HITL confirmation for `record_grid_trade`** — deferred to a future
  Runtime HITL milestone (the requirement basis is AGENTS.md §3.1 item 6;
  ADR 0003 covers automation triggers, not HITL); the web client mitigates
  with a local preview + confirm step meanwhile.
- **`GET /status` nullability semantics** (`signal: null` before the first
  compute) — a documented, intended state; the client renders an empty
  state, no API change.

## 4. Success Criteria

- [x] `GET /trades?limit=2&offset=2` returns the second page with a correct
      post-filter `total`; omitting both parameters returns the first 20
      rows in the envelope. (curl smoke: `limit=1&offset=0/1` paged two
      seeded trades correctly with `total: 2`.)
- [x] `GET /signals` behaves identically (envelope, `offset`, `total`).
- [x] Every 422 from the extension router — pydantic body validation or
      domain rejection — has `detail` as a list of objects carrying
      `loc`/`msg`/`type` (extra keys like `input`/`url` may be present and
      are ignored by clients). Invalid `limit`/`offset` values also land
      on this same 422 path. **Implementation finding**: AgentOS installs a
      global `HTTPException` handler (`agno/os/app.py`) that renders
      `detail` via `str(exc.detail)`, stringifying any list — caught by the
      curl smoke after router-level tests had already passed. Domain
      rejections therefore raise `RequestValidationError` (FastAPI-native
      path, untouched by AgentOS) instead of `HTTPException`.
- [x] `tests/test_etf_grid_api.py` covers all of the above and passes
      (11 tests, incl. new pagination-windowing and invalid-param cases).
- [x] `ruff` / `mypy` / `pytest` (project quality gates) pass.
- [x] A curl smoke run against the dev Runtime confirms the new shapes
      end to end (envelope + all three 422 paths verified on the live
      AgentOS app, 2026-10-12).
