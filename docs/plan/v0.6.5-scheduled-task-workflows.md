## 1. Background

Agno Scheduler supports two execution modes: background Agent/Team/Workflow runs
with status polling and linked run output, or one synchronous request to any
other local HTTP endpoint. The native `/schedules` API already exposes CRUD,
enable/disable, manual triggering, and run history.

Native schedule creation deliberately restricts ordinary users to component run
endpoints for which they have run permission. Scheduling an arbitrary extension
REST endpoint requires `agent_os:admin`. The existing ETF Grid
`POST /api/v1/extensions/etf-grid/refresh` target therefore cannot serve
user-managed personal schedules.

v0.6.5 adopts Agno Workflow as the only new extension execution contribution.
There is no separate Action abstraction, action registry, custom dispatcher,
custom scheduler, or parallel schedule-management API.

## 2. Confirmed Decisions

1. **Use Agno definitions directly.** Extensions contribute Workflow instances;
   a one-step Workflow covers a single operation and a multi-step Workflow
   covers sequential operations. No Runtime Action wrapper is introduced.
2. **Keep Agno-native schedule CRUD.** Runtime verifies and documents the
   framework API rather than adding a parallel router.
3. **Independent sync and recompute.** No strict execution order or cross-
   schedule dependency is introduced. Recompute reads the latest persisted
   shared data available when it runs.
4. **Only the system sync schedule is automatic.** Runtime registers exactly
   one unowned ETF Grid data-sync schedule. It never creates personal
   recompute schedules at startup, during migration, or after ledger writes.
5. **Users manage recompute schedules.** An ordinary user can create, read,
   update, enable, disable, trigger, and delete only their own recompute
   schedules, subject to native Workflow and Schedule scopes.

## 3. API and Execution Contract

### 3.1 Schedule management

The product API remains Agno-native:

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/schedules` | Create a personal schedule |
| GET | `/schedules` | List visible schedules |
| GET | `/schedules/{schedule_id}` | Read one visible schedule |
| PATCH | `/schedules/{schedule_id}` | Update schedule fields or target |
| DELETE | `/schedules/{schedule_id}` | Delete a visible schedule |
| POST | `/schedules/{schedule_id}/enable` | Enable and compute the next run |
| POST | `/schedules/{schedule_id}/disable` | Disable without deleting |
| POST | `/schedules/{schedule_id}/trigger` | Execute an enabled schedule now |
| GET | `/schedules/{schedule_id}/runs` | List visible execution history |
| GET | `/schedules/{schedule_id}/runs/{run_id}` | Read one visible execution record |

Ordinary callers require the native `schedules:read`, `schedules:write`, and
`schedules:delete` scopes for the corresponding operations. Creating, updating,
enabling, or triggering a Workflow target additionally requires permission to
run that Workflow. Administrators retain `agent_os:admin` break-glass access.

Schedule ownership always comes from the verified JWT subject. Request payloads
cannot assign another owner. Public/system schedules remain unowned and are
visible only to administrators through the read API.

### 3.2 Extension Workflow contribution

`ExtensionContribution` gains a `workflows` slot. Runtime flattens extension
contributions and passes them to `AgentOS(workflows=...)` alongside the Team
Leader agent. Workflow ids are stable, extension-prefixed, and suitable for
`/workflows/{workflow_id}/runs` schedule targets.

Workflow steps are deterministic and idempotent in this milestone. They receive
the schedule owner through Agno's native run input; extension code must not
trust a payload-supplied user id. Workflow run records and linked schedule-run
history remain Agno-managed.

### 3.3 ETF Grid Workflows and schedules

| Workflow | Owner context | Steps | Automatic schedule |
|----------|---------------|-------|--------------------|
| `etf_grid_data_sync` | Unowned system execution | Synchronize configured shared market and valuation data | One unowned `etf_grid_daily_sync` |
| `etf_grid_recompute` | Required authenticated/schedule owner | Recompute and persist that owner's grid signals | None |

The system schedule uses the existing `ETF_GRID_SYNC_*` cron, timezone,
enabled, timeout, and retry configuration. Startup registration continues to
converge this code-managed schedule idempotently.

The scheduled system Workflow no longer enumerates ledger owners or computes
their signals. The existing composite `/refresh` route is removed as a
scheduled target; manual shared sync and current-user recompute routes remain
available under their existing authorization rules.

A personal recompute schedule targets
`POST /workflows/etf_grid_recompute/runs`. Multiple users may use different
cron expressions and timezones. No ordering with the system sync schedule is
promised, and no missed recompute is inferred from a sync run.

## 4. Authorization and Isolation

- Add the native Workflow read/run scopes needed by the ordinary user role.
- The accepted implementation uses global `workflows:run`, so ordinary users
  can run and schedule both registered ETF Grid Workflows, including data sync.
- Preserve admin access to all schedules, Workflow runs, and system history.
- Verify two-user isolation for create, list/detail, update, enable/disable,
  trigger, delete, and run history.
- Verify ordinary users cannot repoint a schedule to an arbitrary extension
  HTTP endpoint.
- Preserve native 401/403/404/409/422 semantics and response schemas.

## 5. Scope

### 5.1 In Scope

1. Add extension Workflow contributions and mount them in AgentOS.
2. Verify and document native Schedule write, state-change, trigger, and delete
   APIs in addition to the read contract completed in v0.6.4.
3. Implement deterministic ETF Grid data-sync and recompute Workflows.
4. Repoint the sole automatic system schedule to the data-sync Workflow.
5. Remove scheduled all-user signal fan-out and stop registering personal
   schedules automatically.
6. Use the accepted global Workflow run permission for ordinary users while
   keeping arbitrary extension HTTP targets admin-only.
7. Add unit and real-PostgreSQL integration coverage for Workflow registration,
   CRUD authorization, owner propagation, and ETF Grid behavior.
8. Update architecture and ADR documentation, then run standard quality gates
   and a live JWT CRUD/execution walkthrough.

### 5.2 Out of Scope

- A separate Action model, action registry, generic action endpoint, custom
  schedule router, or custom scheduler.
- Automatic creation, migration, or deletion of personal recompute schedules.
- Strict sync-before-recompute ordering, schedule dependencies, event fan-out,
  catch-up chains, or a global step DAG/parallel orchestration layer.
- Agent/LLM steps, notifications, SchedulerTools, or Web Client UI changes.
- Database schema changes or dependency upgrades unless a pinned Agno defect
  makes one necessary and separately confirmed.

  Workflow run permission permits both ETF Grid Workflow targets; administrators
  retain break-glass access.
- [x] Exactly one unowned ETF Grid data-sync schedule is registered, and no

- [x] System sync performs shared-data synchronization only; personal

- [x] Independent sync and recompute execution works without assuming an
